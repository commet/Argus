## 1. 이 세션이 한 일과 **왜** 했는지

시간순이 아니라 **인과순**으로 적는다. 각 항목의 "왜"가 다음 세션의 판단 기준이다.

### 1-1. 계정 삭제가 모든 사용자에게 깨져 있었다 → 고침

**증상**: `/api/account/delete`가 항상 500. 사용자는 계정을 못 지운다.

**원인 사슬**:
1. `deep_judgment_usage`가 `src/lib/user-data-tables.ts`의 `USER_DATA_TABLES`에
   올라 있었는데, 그 테이블을 만드는 마이그레이션이 **프로덕션에 적용되지 않았다**.
2. 삭제 라우트는 목록을 돌며 `DELETE ... WHERE user_id`를 실행한다. 없는 테이블에서
   PostgREST가 "relation does not exist"를 돌려준다.
3. 라우트의 all-or-nothing 게이트(`hadError`)가 걸려 **auth 신원 삭제를 건너뛴다**.
4. 그런데 신원 삭제는 목록 **밖** 테이블들의 유일한 CASCADE 발화점이다. 그래서 그것들도
   함께 남는다.

**왜 CI가 못 봤나 (이게 진짜 교훈)**: 가드가 둘 있었지만 **둘 다 손으로 쓴 목록을
서로 대조**할 뿐이었다. 두 목록이 같이 틀리면 볼 수 없다. 2026-06-30 `telegram_*`,
07-03 `decision_items`에 이은 **3번째 재발**이다.

**고친 방식** — 목록을 고치는 데서 멈추지 않고 **구멍을 보는 눈**을 만들었다:
- **오프라인(CI)**: `supabase/migrations/*.sql`을 파싱해 user-scoped 테이블을 **기계로
  도출**하고 목록과 대조 (`src/lib/__tests__/erasure-coverage.test.ts`). 리포에 초기
  마이그레이션이 없어 **부분집합 검사**지만, 새 커밋이 깨뜨릴 수 있는 유일한 방향은 막는다.
- **온디맨드**: `scripts/check-erasure-coverage.mjs` — "목록에 있는데 실DB엔 없음"은
  CI가 구조적으로 볼 수 없다. **마이그레이션 후 반드시 실행**할 것.
- `user_id`가 아닌 이름으로 `auth.users`를 참조하는 테이블(`teams`, `team_invites`,
  `anonymous_account_transfer_tickets`)은 `.eq('user_id')` 루프가 **구조적으로** 덮을 수
  없으므로 **사유를 적은 waiver를 강제**했다. 침묵하던 구멍 → 선언된 구멍.
- `mcp_account_authorizations` 추가 — 2026-07-16부터 live였고 `user_id`가 있는데 두 목록
  어디에도 없어 **모든 내보내기에서 빠져** 있었다.
- 오래된 **거짓 주석 정정**: "이 테이블들 중 auth.users CASCADE는 없다"는 처음부터
  사실이 아니었다(실측 51개 FK 중 49개가 CASCADE, 2026-04-09 마이그레이션부터).

### 1-3. 오디세우스 영상은 삭제된 적이 없었다 → 되살림

창업자가 "히어로에서 영상을 날려버렸다"고 지적. 이력을 추적하니:

- `VoyageFilm.tsx`(41KB)도 `voyage-film.mp4`(5.6MB)도 **리포와 CDN에 멀쩡히 있었다**.
- PR #290에서 `SirenHero`가 550줄 재작성되며 **`<VoyageFilm />` 한 줄이 빠진** 것.
- 삭제된 코드의 주석이 의도를 말한다: *"the INPUT is the first-screen focal point,
  not the film"*, *"Odyssey film DEMOTED below"* — **강등하려다 제거로 끝났다.**

창업자가 2번 갈래(히어로 재설계와 함께 복구)를 선택 → 4행 예시 표를 걷어내고 그 자리에
영상을 넣었다. 표는 루프를 라벨 칸으로 **설명**했고, 영상은 같은 네 박자를 **움직임**으로
보여준다(묶기·듣기·닿기·알아봄) — 헤드라인이 한 줄 위에서 말하는 그 논지다.

### 1-4. 영상 자막이 "후다닥 지나가다 멈추던" 문제

**원인**: 스케줄이 **챕터 창 길이를 몰랐다**. 각 절이 0.46~0.85초 상한 + 절 사이 호흡 0
→ 6.6초짜리 챕터가 **1.8초에 다 그려지고 남은 4.8초는 정지 프레임**. 다음 챕터까지의
1.6초 공백이 두 번째 멈춤으로 읽혔다.

**고침**: 각 챕터가 **자기 창을 예산으로** 쓴다(`quoteSchedule`) — 인용이 창의 절반에
걸쳐 그려지고, 절 사이가 쉬고, 꼬리가 한 박자 뒤, 마지막은 읽는 시간.

### 1-5. 전면 가독성 — 타이포그래피가 아니라 스파인 문제였다

프로덕션 캡처를 다시 보니 **제품에서 가장 작은 활자가 곧 provenance**였다:
`AttributedSection` 출처 배지 9px, "실제 당사자의 의견이 아니에요"(모의 검토가 실제
이해관계자가 아님을 밝히는 줄), "AI가 맡은 검토 관점", 회항 칩.

**Argus를 정직하게 만드는 문장들이 화면에서 가장 읽기 어려웠다.** 이걸 키우는 건 장식이
아니라 우정 5조항 ③·⑤의 시공이다. 랜딩 8파일 + 앱 104파일, 총 1,080건을 한 단계씩 상향.

> ⚠️ **방식 주의**: `sed -e` 체인은 **이미 바꾼 값을 다시 바꾼다**(10.5→12.5→14→15.5).
> 1차 시도가 이렇게 세 단계 부풀었고 되돌렸다. **단일 패스 콜백 치환**을 쓸 것.

**부수 수확**: 이 패스가 접근성 테스트 1개를 깨뜨렸는데, 원인이 `<h1>`의 클래스 문자열을
통째로 하드코딩해 **폰트 크기까지 물고 있었기** 때문이다. **글씨를 키우자 접근성 테스트가
실패하는** 뒤집힌 상태였다. 계약을 의도대로 다시 썼다(h1 유지 + **12px 밑으로 못 줄어듦**).

### 1-6. 전제 감시(Brave)를 실제로 태워봄 → 결함 4건

창업자 질문: "이거 웹앱만 있는 거지? 실제로 적용되는 거 맞아?"

**답**: MCP·플러그인엔 **전혀 없다**(grep 0건). 웹앱 전용. 배선은 완전히 살아 있다
(`cron/premise-watch` → `premise-researcher` → `web-research`(Brave)).

**실주행**(프로덕션 키로 진짜 Brave + Claude 호출):
- 금리 전제 → `material`. 2026-07-16 인상(2.50%→2.75%)을 잡고 2026-07-22 발행 출처 인용,
  확신도 high. **전제가 깨진 걸 실제로 잡아냈다.**
- 채용 전제 → `quiet`. 신호가 엇갈린다며 **알리지 않았다**. 과잉발화 절제가 동작한다.
- 최신성 관문 실측: 결과의 **60%만 날짜 보유, 43%만 기준일 통과**. 관문이 실제로 거른다.

**그러다 발견한 결함 4건** (PR #315, 전부 시스템을 **더 조용하게** 만드는 방향):

| # | 결함 | 왜 심각한가 |
|---|---|---|
| 1 | **전제 하나가 그날 밤 전체를 죽인다** | `materiality_rule`은 jsonb(무검증)인데 `evaluateMateriality`가 researcher의 try/catch **밖**. `params` 없는 규칙이면 TypeError가 튀고 크론에도 try/catch가 없어 **GET 전체가 죽는다** → 그날 다른 모든 사용자 미확인 + 이미 계산된 발견 유실(저장이 두 루프 뒤) |
| 2 | **"끄면 멈춰요"가 미결질문에선 거짓말** | `monitoring_enabled`는 MCP가 모든 항목에 주는 스위치인데 `isReconsiderable`이 kind+status만 봐서 무시. **알림 문구가 약속하는 바로 그 항목에서 no-op** |
| 3 | **`<web>` 울타리를 스니펫이 부순다** | 헤더는 "framed so any instructions are ignored"라 주장하나 구분자 미방어. 제목/URL의 리터럴 `</web>`이 블록을 일찍 닫으면 뒤가 지시로 읽힌다. URL은 정화도 안 거쳤다 |
| 4 | **출처 발행일 자리에 오늘 날짜** | 이 기능의 신뢰 모델은 "기준일 이후 발행된 출처만"이고 그 발행일이 알림의 유일한 근거인데, `checked_at`을 "출처:" 괄호에 넣고 `source_date`는 안 썼다 → 근거가 사라지고 출처가 실제보다 신선한 것처럼 과장 |

**덤**: 선언된 중대성 규칙이 **도달 불가**였다. 수치 기준이 있어도 모델에게 안 알려줘
`mode='fact'`를 고르고, 그러면 기계적 임계값이 우회된다(실주행에서 delta 0.25가 정확히
이렇게 건너뛰어졌다). 규칙을 프롬프트에 싣되 `fact` 폴백은 유지 — 강제하면 추출 실패 시
진짜 변화를 놓친다.

## 2. 이 세션에서 반복해 확인된 **한 가지 패턴** (다음 세션이 이어받아야 할 방법론)

> **두 값이 같으면 가드는 차이를 볼 수 없다.**

같은 부류의 실패가 **세 번** 나왔다:

1. 계정 삭제 — 손으로 쓴 두 목록이 **서로만** 대조. 둘 다 틀리면 안 보임.
2. 전제 알림 출처 날짜 — 픽스처가 `checkedAt`과 `source_date`에 **같은 날짜**를 넣어
   어느 쪽을 찍든 통과.
3. 접근성 h1 — 클래스 문자열 통째 하드코딩이라 **개선조차 실패**로 만듦.

**그래서 이 세션의 작업 규율**: 가드를 만들면 **반드시 일부러 망가뜨려 빨간불을 확인**한다.
실제로 이 규율이 한 번 살렸다 — 프롬프트 울타리 검증에서 **초록이 나왔는데 알고 보니
치환이 안 먹은 것**이었다. 변형이 실제로 적용됐는지 확인하고서야 진짜 빨간불이 떴다.
초록을 그대로 믿었으면 **방어가 없는데 있다고 보고**할 뻔했다.

CLAUDE.md의 "무엇이 이걸 빨간불로 만드는가"를 문자 그대로 실행할 것.

## 6. 검증 방법 메모 (다음 세션이 시간 낭비하지 않도록)

- **로컬 dev 서버**: `.env.local`이 없으면 500. 시각 QA용 더미로 띄울 수 있으나
  **세션이 계속 리셋**된다(더미 Supabase). 흐름 검증은 **프로덕션에서** 하는 게 빠르다.
- **`vercel env pull`은 민감 변수를 빈 문자열로 내려준다.** 42개 중 22개가 빈 값이었고,
  분명히 설정된 `SUPABASE_SERVICE_ROLE_KEY`·`NEXT_PUBLIC_SUPABASE_URL`도 빈 값이었다.
  **환경변수 값으로 판정하지 말 것** — 이 세션에서 한 번 잘못된 결론을 내고 정정했다.
- **Vercel 런타임 로그**가 크론 실행 확인의 정답: 넓은 창은 타임아웃되니
  `since`/`until`을 **좁은 창(±10분)** 으로 주고 `group_by: requestPath`부터.
- **Windows 셸에서 한글 curl은 깨진다.** JSON 본문은 `.mjs` 파일로 만들어 `node`로 보낼 것.
- **프로덕션 실호출로 확인 가능한 것**: `/api/search`는 키가 없으면 `disabled:true`를
  돌려주므로 Brave 키 존재 여부를 안전하게 알 수 있다.

### B. 전제 감시가 **실제로 조사까지 도는지** 확인 — 창업자만 가능

지금까지 확인된 것: 크론이 매일 22:30 UTC에 **실행되고 200을 돌려준다**.
확인 **못 한** 것: `PREMISE_WATCH_ENABLED`가 `'true'`/`'1'`인지. 빈 값이면 크론은 즉시
`{ok:true, disabled:true}`로 빠져나간다 — 로그의 200만으로는 구분되지 않는다.

**확인 방법 (창업자)**:
```bash
curl -s "https://argus.voyage/api/cron/premise-watch?dry=1" \
  -H "authorization: Bearer <CRON_SECRET>"
```
`?dry=1`은 **Brave·LLM은 진짜 호출하고 DB 쓰기와 이메일은 건너뛴다** — 안전한 시험 모드.
응답의 `disabled` 필드가 답이다.

감시 대상이 하나도 없으면 `researched: 0`이 나온다. 실제 조사를 보려면 봉인된 영수증에
`auto_watch: true`인 전제가 확인일 도래 상태로 있어야 한다(이 세션에서 심었다가 삭제함 —
재현 SQL이 필요하면 이 문서 §5와 커밋 `aa9c83f1` 참조).
