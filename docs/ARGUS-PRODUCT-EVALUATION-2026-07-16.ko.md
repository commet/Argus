# Argus 제품 평가

- 작성일: 2026-07-16
- 평가 대상: Argus 웹앱, MCP 서버, Claude Code용 driver 및 rich plugin
- 평가 기준: 제품 가치, 차별성, 사용자 경험, 기술 신뢰성, 제품 일관성, 실사용 검증 수준
- 평가 방식: 저장소의 제품 문서·설계 문서·구현 구조·검증 자료·화면 자료를 검토하고, 현재 작업 트리에서 빌드 및 주요 자동 검증을 실행했다.

## 1. 요약 판단

Argus는 아이디어와 기술 기반이 상당히 좋은 제품이다. 다만 현재 상태는 검증된 대중 제품이라기보다, 강한 코어 위에 여러 제품 표면이 겹쳐 있는 완성도 높은 베타에 가깝다.

Argus의 가장 강한 정의는 다음과 같다.

> AI와 함께 내린 결정을 기록하고, 그 결정의 전제와 예측을 나중에 현실과 대조하는 판단 원장.

일반적인 AI 제품이 더 좋은 답이나 추천을 제공하는 데 집중한다면, Argus는 결정 이후의 책임성과 회고에 집중한다.

```text
결정 포착
  → 핵심 전제와 열린 질문 기록
  → 반증 가능한 예측과 확인일 저장
  → 확인일에 실제 결과 기록
  → 당시 판단과 현실을 비교한 Judgment Receipt 생성
```

이 루프는 분명하고 차별적이다. 특히 AI가 사용자의 결정을 점수화하거나 평결하지 않고, 현실이 결과를 답하게 만든다는 철학이 제품 구조에 반영되어 있다.

현재 종합 평가는 약 **7/10**이다. 핵심 MCP 코어만 따로 평가하면 **8.5/10** 수준이다.

| 평가 영역 | 점수 | 판단 |
|---|---:|---|
| 핵심 아이디어 | 9/10 | 실제 문제를 잡았고 차별성이 높다. |
| 기술·신뢰성 | 8/10 | 중요한 규칙이 코드와 상태 전이로 강제된다. |
| 사용자 경험 | 6/10 | 깊이는 있지만 첫 가치까지의 비용이 크다. |
| 제품 정체성 | 5/10 | 웹·MCP·plugin이 서로 다른 제품처럼 보인다. |
| 실사용 가치 검증 | 3/10 | 구조 검증은 강하지만 실제 완료 루프 증거가 부족하다. |

## 2. 제품 구성

현재 저장소에는 사실상 세 가지 제품이 공존한다.

### 2.1 웹앱

결정을 재정의하고, 여러 갈래와 리스크를 탐색하며, AI 작업자와 리뷰를 통해 Current Bearing을 만드는 시각적 제품이다.

주요 경험은 다음을 포함한다.

- 문제 재정의
- 전제와 가설 발견
- AI·사람 역할 분리
- 여러 관점의 사전 검토
- 갈래와 항로 관리
- 예측 봉인과 결과 정산
- Judgment Receipt 및 프로젝트 기록

화면과 브랜드는 일반적인 SaaS 대시보드보다 개성이 강하다. 고전적인 항해 모티프와 편집 디자인은 Argus의 장기적인 결정 여정을 잘 표현한다.

### 2.2 MCP 서버

현재 제품에서 가장 명확하고 완성도가 높은 코어다. 공개 도구는 사용자의 목적을 기준으로 단순화되어 있다.

| 도구 | 목적 |
|---|---|
| `argus_capture` | 결정, 전제, 열린 질문 포착 |
| `argus_predict` | 반증 가능한 예측과 확인일 저장 |
| `argus_check_in` | 현재 확인할 기록 표시 |
| `argus_resolve` | 현실에서 실제로 일어난 결과 기록 |
| `argus_patterns` | 누적된 결정과 영수증 읽기 |
| `argus_settings` | 언어, 알림, 동기화 설정 |

MCP 코어는 평결·추천보다 decision accountability에 집중한다. 로컬 우선 저장, append-only 원장, provenance 분리, 상태 전이 검증이 핵심 강점이다.

### 2.3 Claude Code driver와 rich plugin

`argus-driver`는 MCP를 Claude Code에 연결하고, SessionStart 알림·상태표시줄·진단 기능을 제공하는 얇은 기본 제품에 가깝다.

반면 `argus-plugin-v2`는 여러 스킬, 다중 에이전트, 검증 단계, Boss 리뷰, 별도 세션과 원장 처리를 포함한 고급 의사결정 오케스트레이션 제품이다. 중요한 코드·PR·문서 결정을 깊게 검토할 때는 가치가 있지만, 일상적인 기본 경로로 쓰기에는 비용과 복잡성이 크다.

## 3. 잘된 점

### 3.1 실제 문제를 다룬다

AI는 자연스럽고 그럴듯한 답을 만들지만, 그 답이 실제 결정에 적합한지 또는 나중에 맞았는지는 관리하지 않는다. Argus는 이 공백을 다룬다.

특히 다음과 같은 결정에 잘 맞는다.

- 제품 출시와 가격 결정
- 채용 및 공급업체 선택
- 데이터베이스 마이그레이션
- 큰 리팩터링과 아키텍처 변경
- 시장 진입과 고객 세그먼트 결정
- 되돌리기 어렵거나 결과가 나중에 드러나는 판단

### 3.2 철학이 구조적으로 강제된다

Argus의 신뢰 원칙은 프롬프트 지시에만 의존하지 않는다.

- 평결이나 점수를 내리는 공개 MCP 도구가 없다.
- 예측이 없으면 결과를 기록할 수 없다.
- malformed prediction과 잘못된 상태 전이를 거절한다.
- 원장은 append-only event log로 보존하고 재생한다.
- 사용자 문장과 AI가 제안한 문장의 출처를 구분한다.
- 손상된 마지막 행, 중복 호출, 동시 쓰기 등의 현실적인 실패를 고려한다.
- 한국어·영어 응답과 로컬 환경을 고려한다.

“모델이 사용자를 채점하지 않는다”는 주장이 제품 구조와 일치한다는 점이 중요하다.

### 3.3 축적 가치가 있다

단순한 AI 채팅 기록은 시간이 지나면 다시 읽기 어렵다. Argus는 당시의 결정, 전제, 예측, 실제 결과를 구조적으로 연결한다.

이 정보가 쌓이면 다음과 같은 자산이 될 수 있다.

- 자주 틀리는 전제
- 반복적으로 미루는 확인
- AI 제안을 사람이 수정하는 경향
- 특정 유형의 결정에서 나타나는 낙관 또는 회피 패턴
- 유사한 과거 결정과 결과

이 축적 루프는 단순한 AI 분석 도구보다 장기적인 보존 가치를 만든다.

### 3.4 프라이버시와 소유권 방향이 좋다

MCP 기본값은 로컬 저장이며 원장은 사용자가 읽을 수 있는 JSONL이다. 계정 동기화와 텔레메트리는 opt-in이다. 중요한 판단 기록을 다루는 제품에 적합한 방향이다.

### 3.5 디자인과 브랜드가 구별된다

항해, 귀환, 현실의 응답이라는 서사는 제품의 시간축과 잘 맞는다. Judgment Receipt와 정산 화면도 제품 철학을 시각적으로 전달한다. 브랜드 인지 면에서는 일반적인 AI SaaS보다 강하다.

## 4. 주요 문제와 리스크

### 4.1 제품 정체성이 충돌한다

MCP 코어는 추천·평결·채점을 구조적으로 금지한다. 반면 rich plugin은 Recommendation과 Boss 리뷰 등 적극적인 방향 제시를 기본 산출물에 포함한다. 웹앱은 다시 더 넓은 AI crew와 항해 경험을 제공한다.

이 때문에 사용자는 다음 질문에 명확한 답을 얻기 어렵다.

> Argus는 내 결정을 기록하는 도구인가, 결정을 분석하고 추천하는 도구인가, AI 에이전트 오케스트레이터인가?

핵심 기능이 부족해서가 아니라 제품의 경계가 넓고 상충하는 것이 가장 큰 문제다.

### 4.2 같은 원장 의미를 여러 구현이 소유한다

rich plugin은 MCP 코어를 호출하는 얇은 표면이 아니라, 일부 원장 쓰기·재생·상태 전이 규칙을 별도로 구현한다. 이 구조가 계속되면 같은 행동이 표면마다 다른 결과를 만들 수 있다.

판단 기록과 상태 전이는 제품 신뢰의 핵심이므로 단일 코어가 소유해야 한다.

### 4.3 첫 가치까지의 비용이 크다

Argus의 가장 강한 보상은 예측을 저장한 뒤 현실의 결과를 기록할 때 나타난다. 이 보상에는 본질적으로 시간이 걸린다.

반면 rich plugin의 medium/high 경로는 여러 사용자 질문과 2~4개의 에이전트, 약 4~12분의 실행을 요구할 수 있다. 사용자는 장기 보상을 경험하기 전에 즉시 비용을 지불한다.

첫 세션에서는 다음 네 줄만으로도 가치가 보여야 한다.

```text
내가 선택한 것
이 선택이 기대는 핵심 전제
무엇이 나오면 다시 볼 것인지
언제 현실을 확인할 것인지
```

### 4.4 브랜드 용어가 사용 비용이 된다

Bearing, fog, reef, anchor, crew, Sirens와 같은 용어는 브랜드에는 도움이 되지만 일상 사용에서는 해독 비용을 만든다. 상태표시줄이 일부 항해 용어를 다시 평문으로 번역해야 할 정도라면, 기본 제품 표면도 평문을 우선해야 한다.

MBTI Boss는 제품의 진지한 판단 규율과 충돌할 수 있다. 이해관계자의 역할·목표·권한을 중심으로 한 리뷰는 가치가 있지만, MBTI는 핵심 기능보다 personality-test theater로 보일 위험이 있다.

### 4.5 실사용 가치가 아직 증명되지 않았다

현재 구조·시뮬레이션·퍼즈 검증은 강하다. 그러나 실제 사용자가 예측을 저장하고, 시간이 지난 뒤 돌아와 결과를 정산하고, 이 경험을 반복하는지에 대한 비교군 데이터는 아직 없다.

DKK v6의 P5 가치 관문도 실제 완료 주기와 baseline 비교 자료가 없어 HOLD 상태다. 따라서 다음 주장은 아직 구분해야 한다.

- 말할 수 있음: 코어 상태 머신과 신뢰 규칙이 잘 설계되고 검증되었다.
- 아직 말할 수 없음: 실제 사용자가 장기적으로 계속 쓰는 제품임이 증명되었다.

### 4.6 팀·엔터프라이즈 제품은 아니다

현재 기본 형태는 personal/local이다. 조직용 제품을 주장하려면 다음이 별도 제품 수준으로 필요하다.

- 접근 권한과 역할
- 공유 canonical history
- retention 및 삭제 정책
- redaction과 감사 정책
- 충돌 해결 의미론
- 여러 장치와 여러 host 사이의 안정적인 동기화

## 5. 현재 품질 검증 결과

2026-07-16 현재 작업 트리에서 확인한 결과다.

### 5.1 프로덕션 빌드

- Next.js 프로덕션 빌드 성공
- TypeScript 검증 성공
- 74개 정적·동적 페이지의 build-time 처리가 성공

### 5.2 MCP 테스트

```text
Test Files  2 failed | 88 passed (90)
Tests       4 failed | 893 passed (897)
```

남은 4개 실패는 한국어 OS의 `Intl` 로케일과 테스트가 가정한 영어 기본값 사이의 격리 문제다. 핵심 상태 머신의 대규모 실패로 보이지는 않지만, 로케일은 사용자 표면에 직접 영향을 주므로 릴리스 전에 해결해야 한다.

### 5.3 rich plugin 검증

- plugin 구조 검증 통과
- decision gate 테스트: 22/22 통과
- decision signal 테스트: 68/68 통과
- statusline 테스트: 3개 실패

상태표시줄 실패는 `/argus:settle`에서 `/argus:resolve`로 명령이 바뀐 부분과 아이콘 기반 fog 표시가 `risk:` 평문으로 바뀐 부분을 테스트 기대값이 따라오지 못한 드리프트다. 기능 붕괴보다는 릴리스 마감 불일치에 가깝다.

### 5.4 종합 해석

코어 규율과 구현 품질은 강하다. 다만 전체 릴리스가 완전히 녹색인 상태는 아니며, 로케일과 사용자 표면의 문서·테스트 동기화가 필요하다.

## 6. 가장 잘 맞는 사용자

### 적합

- Claude Code나 MCP를 매일 사용하는 개발자·테크리드
- 중요한 제품 결정을 반복하는 창업자·PM·독립 메이커
- AI의 과도한 자신감과 아첨을 싫어하는 power user
- 자신의 판단 습관을 장기적으로 복기하려는 사람
- 결과가 나중에 드러나는 중요한 결정을 자주 하는 사람

### 현재는 부적합

- 빠른 추천 하나만 원하는 일반 사용자
- 가볍고 되돌릴 수 있는 선택을 주로 하는 사람
- 별도 학습 없이 즉시 화려한 답을 기대하는 사용자
- mobile 또는 remote-only MCP 환경
- 조직 차원의 권한·감사·보존 정책이 필요한 엔터프라이즈 팀

## 7. 권장 제품 방향

가장 설득력 있는 구조는 다음과 같다.

```text
Argus Core
  capture → predict → check-in → resolve → patterns
  모든 host가 같은 원장, provenance, no-grade 규율을 사용

Argus Driver
  Claude Code의 기본 설치
  MCP 자동 배선, 조용한 복귀, doctor, statusline

Argus Review
  중요한 순간에만 사용자가 명시적으로 호출
  코드·PR·문서에 근거한 고급 검토
  결과는 Core에 저장할 draft로 전달
```

### 우선순위

1. MCP를 유일한 판단 기록 코어로 확정한다.
2. plugin의 원장 쓰기와 상태 전이를 MCP Core 호출로 수렴한다.
3. Claude Code 기본 제품은 얇은 driver로 통일한다.
4. rich multi-agent review는 명시적인 고급 모드로 분리한다.
5. 첫 실행을 한 번의 사용자 확인과 한 장의 decision snapshot으로 줄인다.
6. 기본 표면은 평문을 사용하고 항해 용어는 브랜드와 보조 표현으로 제한한다.
7. 첫 resolve에서 통계보다 `then vs now` 비교를 즉시 보여준다.
8. 새로운 persona·agent·pattern 기능은 실제 가치 검증 전까지 확대하지 않는다.
9. 로케일과 statusline 드리프트를 해결해 전체 릴리스 검증을 녹색으로 만든다.
10. 실제 사용자 cohort와 baseline을 통해 P5 가치 관문을 다시 실행한다.

## 8. 실사용 검증 제안

최소 5명의 실제 사용자를 대상으로 21일 동안 관찰하는 것이 적절하다.

### 확인할 퍼널

```text
decision noticed
  → captured
  → prediction accepted
  → check-in surfaced
  → user returned
  → result resolved
  → another decision recorded
```

### 핵심 질문

- 첫 decision snapshot까지 얼마나 걸리는가?
- 사용자 질문이 몇 번 발생하는가?
- 제안된 prediction을 실제로 저장하는 비율은 얼마인가?
- 확인일에 Argus가 다시 보였는가?
- 창업자의 별도 재촉 없이 전체 루프를 닫았는가?
- 첫 Judgment Receipt가 다시 사용할 이유를 만들었는가?
- Argus가 사라졌을 때 사용자가 아쉬워할 구체적인 순간이 있는가?

### 해석 원칙

구조 테스트나 AI 시뮬레이션만으로 GO를 선언하지 않는다. 실제 완료 주기와 비교군 비용이 확보될 때까지 제품 가치 평가는 HOLD로 유지한다.

## 9. 최종 결론

Argus는 좋은 제품의 씨앗을 넘어, 이미 강한 핵심 제품을 갖고 있다. 문제는 그 주변에 여러 제품 표면과 기능이 너무 빨리 확장되었다는 점이다.

현재 Argus를 가장 정확히 평가하면 다음과 같다.

> 써볼 가치가 있는 강한 베타. PMF가 검증된 완제품은 아니지만, 흔한 AI 래퍼와 달리 살아남을 만한 독자적인 원리와 신뢰 구조가 있다.

Argus가 지금 더 필요로 하는 것은 추가 기능이 아니다. 하나의 코어, 짧은 첫 가치, 조용한 귀환, 실제 사용자 완료 루프의 증거다.
