| | |
|---|---|

| 그 플러그인이 띄우는 서버 | `npx -y argus-decision-mcp@1.10.0` |

당신 환경이라 **허락 없이 업데이트하지 않았습니다.** 격리된 프로필에서 같은

위 한 줄이면 됩니다.

## 1. 이번에 잡은 것 — Codex에서 Argus는 사실상 안 됐다

### 재현 (실제 `codex app-server`, 같은 Argus 빌드, 다섯 설정)

| 승인 정책 | 확인창이 화면에 도달하나 | 사용자가 본 것 |
|---|---|---|
| 기본값 | **예** | 정상 저장 |
| `approval_policy = "never"` | **아니오** — Codex가 ~330ms 만에 스스로 decline | `"Not recorded."` |
| `granular.mcp_elicitations = false` | **아니오** — 같음 | `"Not recorded."` |
| 허용 + 사람이 Decline | 예 | `"Not recorded."` |

아래 세 줄이 **똑같이** 보인다는 게 핵심이다. Codex가 대신 답한 것을 우리는
`choice: "declined"`로 기록하고 있었다 — **아무도 안 한 결정을 사람 것이라고
적은 것.** CLAUDE.md 스파인 1번(저자를 속이지 않는다)에 정면으로 걸린다.

### 프로토콜로는 구분이 안 된다 (조사 완료)

Codex app-server 스키마를 직접 뽑아 확인했다.
`McpServerElicitationRequestResponse` = `action`(accept/decline/cancel) +
`content` + `_meta`(실제로 null로 옴). **정책 거절 표시가 없다.** 앞 세션이
"먼저 조사할 것"으로 남긴 후보 A는 이걸로 반증됐다.

### 그래서 무엇을 하기로 했나

정직하게 말할 수 있는 건 딱 하나: **방금 그려진 폼이 500ms 안에 거절돼 돌아왔다면
아무도 그걸 읽지 않았다.** 이건 읽는 속도에 대한 진술이라 호스트 이름 목록이
필요 없고, **"그 거절을 사용자 것이라고 주장하기를 거부"하는 근거로만** 쓴다.
사용자에 대한 결론을 내리는 근거로는 절대 쓰지 않는다.

- 읽을 수 없이 빠른 거절 → `no_answer`. 기록 0, 귀속 0, 텍스트 경로 제시
- ambient(묻지도 않은 질문)만 예외로 쿨다운을 소진한다. 여기서만 두 해석이
  같은 답을 낸다 — 정책이면 보이지 않는 타이머가 영원히 재시도, 사람이면 방금
  거절한 이에게 다시 미는 것. 둘 다 멈추라고 한다
- 영어 문구에서 "the dialog closed"를 뺐다. 차단된 호스트에선 창이 뜬 적이 없다

### 앞 트랙의 설계는 가져오지 않았다 (중요)

Codex 트랙 WIP는 **첫 번째** 빠른 거절에 **세션 전역 차단기**를 열었다. 그건
사람이 그냥 빨리 답해도 걸리고, 걸리면 그 세션의 정산 픽커·연기 픽커·전제
픽커가 전부 사라진다. 그 트랙이 보고한 빨간불 3종(E2E 4실패 · battery S36 RED ·
picker-surfaces 32위반)이 전부 이 차단기 때문이었다.

거래를 다시 계산했다: 차단된 호스트에 한 번 더 묻는 비용 = 아무도 못 보는
요청 1건(측정상 ~0ms). 잘못 짚었을 때 비용 = 사용자의 이후 모든 화면. **비교가
안 된다.** 그래서 **ask는 절대 억제하지 않는다.** 관측 패턴(연속 2회, 반증이
하나라도 오면 리셋)은 `argus_check_in`이 **보고하는 표면 종류**만 바꾼다.

결과: E2E 13/13, battery 0 RED, picker-surfaces 6696/0.

## 5. 다음 세션에 당부 (앞 문서 §9에 더함)

6. **하네스가 실패를 스스로 만들어내면 하네스만 증명한다.** Codex 게이트의 첫
   판은 메시지에 `auto-reject`가 들어 있으면 하네스가 거절하는 방식이었다. 그건
   Codex의 정책 거절이 아니라 우리가 쓴 if문이다. 실제 정책으로 Codex가 직접
   만들게 해야 한다.
7. **0ms에 답하는 하네스는 빠른 사용자가 아니라 기계다.** 사람의 행동을
   검사한다고 주장하는 시나리오는 사람처럼 굴어야 한다. (battery의 `humanPause`가
   그 선언이다 — 초록 만들려고 넣은 sleep이 아니라, 어느 현실을 시험하는지
   시나리오가 밝히는 것. 반대쪽 현실은 별도 시나리오 S36b를 가진다.)
8. **맞을 수 없는 마커는 낡은 마커보다 나쁘다.** 배포본에만 대보면 "빠진 수정"과
   "틀린 마커"가 똑같은 빨간불이다. 방금 만든 로컬 빌드에 먼저 대보면 갈린다.
9. **다섯 파일이 서로 일치해도 사람이 복사하는 줄이 틀리면 그 사람에겐 제품이
   없다.** 게이트는 문서의 설치 핀까지 봐야 한다.

## 6. 픽커를 실제 Codex 배선에서 두 언어로 읽고 고친 것 (추가분)

앞 절들이 "동작하나"였다면 이건 "읽을 수 있나"다. 실제 `codex app-server`가
클라이언트로 넘기는 payload를 그대로 찍어서 한국어·영어 네 화면을 눈으로 읽었다.

| 결함 | 무엇이 문제였나 |
|---|---|
| **호스트마다 다른 키보드를 한 문장에 박아둠** | 네 개 메시지가 Claude Code의 TUI 조작법을 그대로 적고 있었다 — `→ 키로 하나 고른 뒤, 아래 화살표로 수락 줄까지 내려가`, `press Enter twice to reach Accept`. Codex에서 폼을 보는 사람에게는 **없는 키를 누르라고 말하는 것**이고, 마우스를 쓰는 데스크탑 사용자에게도 마찬가지다. 밑에 깔린 사실은 호스트와 무관하다: **고르기만 해서는 저장이 안 되고, 답은 Accept에서 들어간다.** 그렇게 고쳤다 |
| **칸 설명 안의 줄바꿈** | `what_happened` 설명에 줄바꿈 문자가 들어 있었다. `message`는 호스트가 잡아주는 블록이지만 칸 설명은 입력창에 붙는 힌트라 호스트마다 다르게 다룬다 — 실제로 둘째 문장이 칸 밖으로 흘러나왔다 |
| **영어를 또 아무도 안 읽었다** | 전제 기록 확인 문구의 한국어는 "잘못 적혔으면 말씀해 주세요, 바로잡은 내용도 기록에 남습니다"인데, 영어는 **사람에게 `argus_capture`를 호출하라고** 했고 안심 문구는 통째로 빠져 있었다. 도구 이름은 모델이 읽는 `next_actions`의 몫이다. 재확인 안내도 붙여 쓰다 보니 영어만 133자 벽이 됐다 (한국어는 밀도가 높아 우연히 통과) |
| **doctor가 네 항목을 말없이 건너뜀** | 바인딩이 없으면 `[1] [2] [7] [8]…`로 찍혀서, 읽는 사람이 "네 개가 실패한 건가"를 스스로 판단해야 했다. 진단을 돌리는 사람은 이미 불안한 상태다 |

**게이트도 같이 고쳤다.** 제출 안내를 검사하던 게이트는 두 번 데었다 — 처음엔
문구 하나를 리터럴로 찾아서 카피가 **좋아졌는데** 빨개졌고, 그 다음엔 한 호스트의
조작법만 인정해서 **틀린 카피를 강제**했다. 이제 "Accept로 이어지는 안내"라는
의미를 본다. `picker-surfaces`에는 "칸 라벨·설명은 한 줄" 128개 검사가 붙었다
(되심어 8건 빨간불 확인).

**이 시점 게이트** (합류 전 수치 — 최종은 §7): 단위 1120 · picker-surfaces 6824/0 · surface-hazards 1222/0 ·
host-matrix 424/0 · battery 95 calls 0 RED · claude-code-form 120/0 ·
real Codex 15/0 · E2E 13/13 · keepsake 254/0 · version-lockstep 11/0.
`verify-all` 전량 1회: **전 게이트 통과 + 심은 회귀 24개 전부 잡힘, 트리 원상복구.**

## 7. 병렬 트랙과의 합류 (2.0.6이 먼저 나갔다)

작업 도중 Codex 트랙이 PR #321로 main에 합류했고 **2.0.6으로 태그·npm 발행까지
끝냈다.** 그래서 이 작업은 **2.0.7**이 된다.

**두 트랙이 독립적으로 같은 결론에 도달한 것:** 세션 전역 차단기는 없어야 한다.
그쪽도 지웠다. 이건 서로 다른 경로에서 같은 답이 나온 것이라 신뢰도가 높다.

**남은 차이는 딱 하나 — 안 보인 거절을 뭐라고 부를 것인가.**

2.0.6의 논거: 경과 시간으로는 정책 자동거절과 빠른 사람을 못 가른다 —
*"테스트·접근성 자동화·키보드 사용자·이미 답을 아는 사람 모두 즉시 응답할 수
있다."* **전부 사실이고, 특히 접근성/키보드 사례는 내가 앞서 답했던 반례들보다
낫다.**

다만 그건 **결론 내리지 말라**는 논거지, **"사용자가 거절했다"고 보고하라**는
논거는 아니다. 실측한 대로 `approval_policy="never"`에서는 요청이 렌더링될 수
있는 어디에도 닿지 않고 Codex가 ~330ms에 대신 답한다. 그걸 사용자 것이라 적으면
아무것도 못 본 사람에게 결정을 씌우고, 빠져나갈 길도 안 준다.

그래서 **행동은 귀속을 거부**하고(기록 0·귀속 0·텍스트 경로), **문장은 두 해석
모두에서 참이도록** 다시 썼다:

> 기록하지 않았습니다. 확인 창을 보지 못하셨다면 호스트가 대신 답했을 수 있습니다.

양쪽 다 참인 사실(기록 안 됨)로 시작하고, 호스트 설명은 **조건절**로 둔다 —
일부러 거절한 사람에게 "답이 오지 않았습니다"라고 하는 건 그가 방금 한 일을
부정하는 것이기 때문이다.

main의 해당 단언은 **그 자리에서 뒤집되 이유를 옆에 적어** 두었고, 두 트랙이
합의한 절반(ask는 계속 나간다 · 거절 한 번이 이후 픽커를 안 없앤다)은 그대로
단언한다.

**main에서 그대로 가져온 것 (그쪽이 더 낫다):**

- `verify-all`이 자기검증을 **폐기 가능한 복사본**에서 돌리고, 단순 비정상 종료가
  아니라 **그 게이트 고유의 실패 문구**를 요구한다 — 내 것보다 확실히 강하다
- `supportsReliableElicitation()` (제품명 아닌 capability 기준)
- capability 프로브를 **seam에서 강제**하고, 프로브 자체가 throw하면 **닫히는
  쪽으로 실패** — 예외는 capability의 증거가 아니다
- `ARGUS_TEST_RUN_ID`로 fixture 루트 분리 (verify의 동시 실행 충돌 방지)
- publish 워크플로의 Claude CLI 설치 형태(`--allow-scripts`·버전 고정) — npm 11에서
  평범한 `npm i -g`는 네이티브 바이너리를 안 깔아 CLI가 못 돈다. CI도 이 형태로 맞췄다

## 8. 릴리스 경합 — 창업자 판단이 필요한 한 가지

이 세션이 도는 동안 병렬 트랙이 **2.0.6 → 2.0.7 → (pack 메타 수정)** 을 연달아
태그·발행했다. 나는 그때마다 main을 다시 합치고 전량 재검증했다. 결과물은
2.0.8이고 품질 손실은 없다 — 오히려 그쪽 게이트 두 개(POSIX 실행 비트, 패키지
실행성)를 받아왔다.

다만 **한 패키지에 두 트랙이 몇 분 간격으로 릴리스를 밀고 있다.** 재합류 한 번에
전량 재검증(20분+)이 붙고, 그 사이 또 나갈 수 있다. 이건 기술 문제가 아니라
조율 문제라서 내가 혼자 정하지 않았다. 가장 단순한 형태:

> **릴리스 버튼은 한 트랙이 쥐고, 다른 트랙은 그 위로 착지한다.**

나는 태그 경쟁을 하지 않고 항상 합류 가능한 상태를 유지했다.

**참고:** GitHub이 PR #319를 `CONFLICTING`으로 표시할 수 있는데 **stale이다.**
`git merge-base --is-ancestor origin/main HEAD`가 참 — main이 내 HEAD의 조상이라
병합은 fast-forward고 충돌이 불가능하다. 이 레포는 Actions 이벤트가 멈춘 전력이
있다(§CI는 `gh workflow run CI --ref <branch>`로 수동 트리거).
