## 1. 무엇이 문제였나

창업자가 2026-07-27~28에 걸쳐 세 번 보고했다:

> "확인창에서 Accept를 눌러도 기록이 안 된다."

앞선 두 세션이 각각 고쳤다:

| 시도 | 무엇을 고쳤나 | 진짜 결함이었나 | 원인이었나 |
|---|---|---|---|
| 1차 | 픽커 스키마의 `required` 제거 | **예** | 아니오 |
| 2차 | `format: "date"` 제거 | **예** | 아니오 |
| 3차 (이번) | 확인창에서 **입력칸 자체를 제거** | 예 | **예** |

앞의 둘은 진짜 결함이었다. 다만 원인이 아니었고, 매번 게이트는 초록이었다.

### 진짜 원인

배포된 Claude Code 바이너리(v2.1.220)를 직접 읽어 확정했다:

```js
const hasFields = Object.keys(schema.properties).length > 0
const [selected] = useState(hasFields ? null : "accept")   // 필드 있으면 Accept 미선택
handleTextInputSubmit = () => move("down")                 // 칸 안에서 Return은 "이동"
if (key === "return" && selected === "accept") { …제출… }
```

**픽커가 입력칸을 하나라도 선언하면 Accept가 처음부터 선택되지 않는다.** 커서는 첫 칸에
있고, 거기서 Return은 다음 줄로 이동할 뿐이다. 봉인 확인창은 `reword`·`check_by` 두 개의
**선택** 편집칸을 보내고 있었다. 그래서:

1. 사용자가 예측을 읽고 Accept를 누른다 → 아무 일도 안 일어난다
2. 60초 뒤 MCP SDK 기본 타임아웃이 걸린다
3. 호스트가 그것을 `cancel`로 보고한다
4. 도구는 "기록하지 않았습니다"라고 말한다

창업자 호스트 로그의 **60.018초 `cancel`** 이 그것이다. 아무도 누르지 않은 취소였다.

### 왜 세 번이나 못 잡았나

**하네스가 전부 즉시 답했다.** 사람이 결코 하지 않는 유일한 행동이다. 우리는
"픽커가 뜨는가", "스키마가 유효한가"는 검사했지만 **키를 몇 번 눌러야 제출되는지**는
아무도 재지 않았다.

## 2. 실기기 검증에서만 나온 것 2건

기계 검증이 **전부 초록인 상태에서** 실제 Claude Code를 띄워 직접 눌러보니 두 개가 더
나왔다. 이게 §4(실기기)를 건너뛰면 안 되는 이유다.

### 2.1 화면은 "(선택)", 서버는 필수

정산 픽커의 what-happened 칸이 `(optional)` 라벨에 "모르면 비워두세요"라고 안내했다.
안내대로 결과만 고르고 비워서 제출하면:

```
WHAT_HAPPENED_REQUIRED — 실제로 일어난 일을 기록해야 합니다
```

게다가 그 거절이 **아무것도 돌려주지 않아** 모델이 사용자에게 결과를 **다시 고르라고**
했다. 사용자가 답했는데 그 답이 버려지고 재입력을 요구받는 구조다.

**수정:** 라벨을 조건부로 바꿨다 — 모델이 이미 문장을 가져온 경우에만 "(선택)"이고,
아니면 "결과를 남기려면 이 줄이 필요합니다"라고 말하고 "아직 모르겠다" 선택지를 가리킨다.
거절은 사용자가 고른 결과를 되돌려준다. **`minLength`는 넣지 않았다** — 제약을 걸면
폼 안에서 Accept가 막히는데, 그게 바로 §1의 결함이다.

### 2.2 기록이 답변보다 63초 앞섬

미결질문을 픽커에 타이핑해 닫았더니:

```
12:56:11  원장:   premise_resolve "split it, and price the tiers separately"
12:57:14  호스트:  Elicitation response {"decision":"split it, and price…"}
```

핸들러가 진입 시점에 시각을 찍고, 그 뒤 픽커가 사람을 기다렸다(62초). 아무것도 잃지
않았지만 **정직한 기록을 위조된 것처럼 보이게 한다** — 실제로 그 payload를 본 리뷰
세션이 "서버가 판단을 지어내 `user`로 찍었다"고 결론냈다. 아니었다. 내가 친 말이었다.

**수정:** `settle`은 이미 픽커 뒤에 찍고 있었다. `seal`과 미결질문 resolve도 같게 했다.
논리적 **날짜**는 그대로 두고 시각만 바로잡는다.

## 4. 새로 만든 게이트 (전부 고장난 버전에서 빨간불 확인함)

| 파일 | 무엇을 지키나 | 판별력 증거 |
|---|---|---|
| `evals/claude-code-form.mjs` | Claude Code의 **실제 제출 게이트**를 그대로 구현해 전 픽커 판정 + **키 횟수** | **2.0.2에서 빨간불** |
| `evals/answer-time.mjs` | 느리게 답하고, 기록이 답변보다 앞서면 실패 | 두 수정 각각 되돌려 빨간불 |
| `evals/slow-human.mjs` | 75초 뒤 Accept가 살아남는지 | timeout 옵션 제거 시 빨간불 |
| `evals/keepsake-frames.mjs` | 액자 254 checks, **독립된 자**로 측정 | 6결함 각각 되심어 빨간불 |
| `evals/version-lockstep.mjs` | 5곳 버전 일치, 특히 npx 핀 | 핀만 낮춰 빨간불 |
| `host-matrix.mjs` D2 블록 | 서버가 요구할 칸을 "선택"이라 부르지 않는다 | 라벨 되돌려 7호스트 빨간불 |

**게이트를 만들 때의 원칙 (이번에 비싸게 배운 것):**

- **검사기는 대상과 독립된 근거로 재야 한다.** 이모지 폭 결함이 안 보였던 이유는 검사
  코드가 렌더러 자신의 폭 함수를 import했기 때문이다. 둘 다 같은 방향으로 틀리면
  영원히 안 보인다.
- **하네스가 즉시 답하면 시간 관련 결함은 못 잡는다.**
- **문구가 아니라 의미를 검사하라.** 게이트가 `Enter를 두 번`이라는 특정 표현을 찾고
  있어서, 그 문구를 더 나은 한국어로 바꾸자 빨개졌다.
- **도달 불가능해진 코드는 테스트할 수 없다.** 봉인에서 필드를 없애자 "타이핑한 말
  돌려주기" 보호가 어떤 호스트에서도 실행되지 않게 됐고, 그 자기검증은 회귀를 심어도
  초록이었다 — *게이트가 거짓말을 시작한 순간*. `extra-field` 호스트 프로필을 추가해
  그 경로를 살렸다.

## 7. 지금 열려 있는 것

### 🔴 배포본(npm 2.0.4)과 main이 갈려 있다 — 가장 먼저 볼 것

PR #308을 머지한 뒤 확인한 사실이다. **버전은 양쪽 다 2.0.4인데 코드가 다르다.**

```bash
git diff --stat v2.0.4 origin/main -- argus-mcp/src
#  seal-provenance-replay.test.ts | 68 +++
#  ledger-append.ts               |  6 +
#  ledger-replay.ts               |  7 +
#  seal.ts                        |  8 +-
```

PR #308이 MCP에 실질 수정을 담고 있었다 — 봉인 이벤트 자체에 `predicate_owner`를 실어
웹 다리를 건널 때 출처가 유실되지 않게 하는 것. **CLAUDE.md 규칙 1(저자를 속이지 않는다)에
해당하는 수정이고, npm 2.0.4에는 없다.** 직접 확인했다:

```bash
npm pack argus-decision-mcp@2.0.4 --prefer-online && tar xzf *.tgz
grep -c "predicate_owner: a\['predicate_owner'\]" package/dist/index.js   # → 0
```

**왜 게이트가 못 잡았나:** `version-lockstep.mjs`는 *다섯 파일의 버전 문자열이 서로
같은지*만 본다. 소스가 바뀌었는데 버전이 안 오른 경우는 검사 범위 밖이다. 오늘 만든
게이트의 빈틈이고, 이 문서를 쓰는 시점에 아직 안 메웠다.

**해야 할 일 (택일):**
- **2.0.5를 내보낸다** — 출처 수정이 사용자에게 도달해야 한다면. 버전 5곳 올리고
  `evals/verify-published.mjs`의 `BUNDLE_MARKERS`에 `predicate_owner` 마커를 추가한 뒤
  main에서 `v2.0.5` 태그
- **다음 릴리스에 묶는다** — 급하지 않다고 판단되면. 다만 그때까지 main ≠ npm 상태가
  유지된다는 것을 알고 있어야 한다

**같이 고려할 것:** "배포된 태그 이후 `argus-mcp/src`가 바뀌었는데 버전이 그대로면
빨간불" 게이트. 이 상황이 조용히 반복되는 것을 막는다.

### 검증 체계 관련

- verify가 22개 자기검증 × 재빌드로 **20분+** 걸린다. 디스크·시간 압박이 커지고 있어
  분할 실행(게이트만 / 자기검증만)을 고려할 만하다
- `verify-published.mjs`는 `verify-all.mjs`에 **넣지 않았다** — 그건 레지스트리에 이미
  올라간 것을 검사하므로 배포 전에는 돌 수 없다. 배포 직후 손으로 돌리는 단계로 남긴다

## 9. 다음 세션에 당부

1. **"게이트 초록"과 "사용자가 쓸 수 있다"를 같은 말로 쓰지 마라.** 이 사태의 뿌리다.
   초록불은 *우리가 검사할 생각을 한 것*만 통과했다는 뜻이다.
2. **실기기를 건너뛰지 마라.** §2의 두 결함은 기계 검증 전부 초록인 상태에서 나왔다.
3. **의심스러우면 바이너리를 읽어라.** 세 번째 시도에서야 그렇게 했고, 그제야 잡혔다.
4. **창업자의 실행 중인 터미널 창에 키를 넣지 마라.** 새 창에서만. Windows Terminal은
   새 창 요청을 기존 창의 **탭**으로 붙일 수 있다 — `MainWindowHandle`이 0이면 남의 창에
   들어간 것이다. `claude` 프로세스를 **이름으로 죽이지 마라**(다른 워크트리 세션까지
   죽는다).
5. **디스크가 부족한 상태에서 돌린 결과는 버려라.** 이번에 창업자가 정확히 지적했고,
   전부 재실행했다. "되겠거니" 하고 넘긴 것이 나중에 문제가 된다.
