> 기존 계획(`ARGUS-2.0-PLAN-2026-07-02.md`, `UNIFIED-REMODEL-PLAN-2026-07-02.md` 등)은
> **특정 사실을 보강할 때만 각주로 인용**한다 — 권위나 뼈대가 아니다.
>

## 0. 결론 (정직한 스코프)
progressive의 **컨셉·야심은 옳다**(유지). 그러나 현재 **구현은 신뢰성·정보구조·목소리에서 근본적으로 미완**이다.
이건 폴리시로 덮을 문제가 아니다 — 일부는 **대공사(재아키텍처)**다. "수술이면 충분"이라는 앞선 내 프레임은
낙관이었고, 아래 §2에서 항목별로 대공사/수술/폴리시를 가른다.

## 1. 직접 관찰한 것 (1차 근거 — 이 문서의 뼈대)

### 1.1 신뢰성 — 코어가 안 돈다 (가장 심각)
- **듣기(멀티에이전트) 팀분석이 0/5에서 멈춤.** "중단된 작업이 있어요 · 다시 실행" 배너. 캡처 간 **플래키**: 어떤 회차는 "팀 분석 완료", 어떤 회차는 0/5 정지.
- **단계 전체 크래시.** "이 단계에서 문제가 생겼어요 · 새로고침"(ErrorBoundary).
- **지연 53–57s** "오래 걸리고 있어요". 크루 5명 + 긴 합성 + 재시도.
- **함의:** "다시 실행" 복구 UI가 존재한다는 건 중단이 상시라는 뜻. 재실행이 처음부터면 토큰 재소모.
  → 이건 UX가 아니라 **실행 엔진 재설계** 문제. (코드: `ProgressiveFlow.tsx`, `useProgressiveStore.ts`,
  `progressive-engine.ts`, `lead-agent.ts` — 조사 대상.)

### 1.2 정보구조 — "안 읽는다"
- **front-load / 벽.** 매 화면이 재정의 + 숨은 전제 3 + 5단계 계획 + 질문을 **동시에** 쌓음. 이름은
  progressive인데 실제로는 front-load. 스크롤이 화면마다 거대.
- **통합분석(민재)이 수학 벽.** 좌석수·손익분기 계산 문단이 결정 성격과 무관하게 매번. 아무도 안 읽음.
- **가치 역전.** 제품 최고 가치(CEO 검토·flinch 봉인)가 그 안 읽는 벽 **아래**에 깔림.
- **크로스-페이즈 반복.** 방향·답변 pill·5단계가 묶기/듣기/검토마다 재출력.
- **듣기 페이즈 과부하.** 팀분석+초안+CEO검토+flinch봉인이 한 페이즈에. 묶기·닿기는 얇음.
- **로딩=풀콘텐츠.** "분석 중"인데 전체가 이미 렌더됨 → 완성 시 재렌더/점프.
- → 상당 부분이 CSS가 아니라 **플로우 아키텍처 재설계**(진짜 progressive disclosure + 페이즈 재분배).

### 1.3 목소리/콘텐츠
- **합성(민재)이 정량 디폴트.** 결정이 정성적이어도 산술부터. → **합성 프롬프트 재설계**(결정 성격에 목소리 적응).
- **메타포/자곤 — 대부분 실체 없음(2026-07-03 소스 검증).** 캡처에서 의심한 `솔 출항`·`펼쳐서요`·`징을 탭`·
  레일 `당기`·`다현규서`는 **소스에 리터럴 없음**(저해상도 오독 or 런타임 조합 or 기수정). 모지바케도
  mojibake 가드 593개 통과로 **이미 해결**. 실재하는 건 `닫은 고리`(record-summary.ts) 뿐이고 이건 버그가
  아니라 **의도된 은유**(정산=닫힌 고리) — 명료성 재고 대상이지 결함 아님. → **Tier 2의 카피 작업은 거의
  없다. 진짜 Tier 2 = 합성 정량 디폴트(1.3 상단) 하나.** 유일한 잔여 크루 극장 이슈: 0/5 stall 시 "일하고
  있어요"가 거짓처럼 보이는 것 — 이건 카피가 아니라 신뢰성(1.1) 고치면 사라짐.

### 1.4 봉인/해자 (논지의 심장 — 개념 정합 + 데이터 정합)
- **봉인이 3개** — 마음 기울기(묶기) / flinch(듣기) / 예측(닿기). 의도된 3단인지, 중복·혼란인지 **개념 재정의 필요**.
  (사용자 증언: "다 구현은 안 된 것 같다".)
- **봉인 직후 이탈 시 산출물 서버 미도달.** 저장이 trailing debounce인데 unload flush가 없어, 완성·봉인 후
  바로 나가면 최종본이 영영 안 닿을 수 있음. **해자-치명.** (독립 확인: 기존 감사에도 F13으로 동일 지적.)
- **focus 모드가 안 본 AI 분석에 자동 날인** → 출처 세탁·학습신호 오염(스파인 위반). (독립 확인: F10.)
- **정산(settle) 뒷단은 실재**(`SettlementModal`·`settle-align`·`checkin-reminder`·`api/cron/checkin-due`) —
  단, **progressive發 예측의 정산 경험이 봉인만큼 좋은지 + 익명→로그인 마이그레이션(`account-migration.ts`)이
  봉인/세션을 보존하는지** 검증 필요. (`progressive_sessions`는 user-scoped 동기화 테이블 — `user-data-tables.ts:32` 확인.)

### 1.5 폴리시
- 해도 필기체가 양피지 위라 실제 질문 라벨 판독 불가. 진입 카피("AI 팀이 갈리는 자리") 모호. seal-first 오디세우스 카피 과다.

### 1.6 지켜야 할 것 (회귀 위험)
seal→settle 루프 · flinch-to-seal · CEO검토(→최종 문서 실제 반영) · 내 생각 추가 · 정직한 provenance ·
내용 엔진(재정의·전제·분기) · 항해일지 · 공유 허브(이메일/Slack/Telegram end-to-end) · 해도 분기.

## 2. 대공사 vs 하자보수 — 항목별 정직한 구분

|------|--------|-----|

| 진짜 progressive disclosure + 페이즈 재분배(1.2) | **대공사(재설계)** | 벽·front-load·가치역전·듣기 과부하는 CSS가 아니라 정보 아키텍처 문제. |

## 3. 실행 순서
1. **Tier 0 — 엔진 안정화(대공사):** 0/5 stall·크래시 root-cause → 멀티에이전트 실행 모델 재설계 + 속도.
   동시에 국소 핫픽스(seal-flush unload, 자동날인 제거)로 데이터/스파인 출혈 지혈.
2. **Tier 1 — 정보 아키텍처(대공사):** front-load 해체 → 진짜 disclosure, 가치 위로/분석 벽 아래, 반복 제거,
   듣기 페이즈 분해, 로딩=스켈레톤. **모바일 우선 검증.**
3. **Tier 2 — 목소리(재설계):** 합성 정량 디폴트 끄기(결정 성격에 목소리 적응). (메타포/자곤/오타는 검증 결과 불필요 — 삭제.)
4. **Tier 3 — 폴리시:** 해도 라벨 가독, 지연 체감.
5. **Cross-cutting:** 봉인 모델 정의(1.4) · 정산/마이그레이션 검증 · 재방문자 경량화(해자=반복) · 크루 규모를 stakes에 스케일(over-fire).

  AI 없는 크루(전부 `waiting_input`)면 헤더가 "일하고 있어요"를 영원히 표시(플로우는 이미 넘어감).

- **○ Q3 — 수정 불필요.** "다시 실행"은 이미 완료 워커를 건너뛰고 재개(토큰 재소모 없음, `worker-engine.ts:219`).
- **○ Q5 — 코드 불필요.** focus 자동날인은 이미 제거됨(`ProgressiveFlow.tsx:1434-1441`); focus는 게이트만

- **⏸ Q4 — 봉인 서버-도달 (band-aid 금지, 스펙만 남김).** 봉인 계약은 project-store upsert(`db.ts:232`,
  fire-and-forget, keepalive/unload flush 없음). 순진한 keepalive는 **64KB 상한**에 걸림 — 봉인이 프로젝트
  *전체*(큰 문서)를 upsert하므로 큰 프로젝트에서 조용히 실패 = 또 다른 하자보수. **제대로 된 fix:**
  (a) 계약만 담는 소형 전용 write 경로(decision_contract only) + keepalive, 또는 (b) cookie-auth라면
  `/api/…` 엔드포인트로 `sendBeacon`. **실제 auth/deploy 환경 검증 필수**(로컬 시크릿으로 검증 불가) →
  전용 sub-task로. 참고: 같은-기기 재방문 시 localStorage 병합으로 복구되므로 손실 범위는 "봉인 직후
  닫고 즉시 타기기 전환"으로 좁음.
