## 한 문단 요약 (비개발자용)

Argus의 진짜 가치는 "결정을 봉인하고 → 몇 주 뒤 현실과 대조해 정산한다"는 데 있는데,
지금 그 쌓인 기록을 **다시 보여주는 화면이 거의 없다.** 감사 08이 처방한 S1~S7 중
"보물이 보이는 최소 완결"(S1 판단 액자·S2 자차표 한 뇌·S3 대문 항적·S5 3고리 의식·S7 카피)은
**이미 이 워크트리에 다 들어와 있다**(코드로 확인). 남은 건 딱 두 조각 — **S4 함대 해도**
(쌓인 배들이 한 장의 해도 위에 늘어서는 그림)와 **S6 항해일지**(봉인·변침·정산을 시간순 원장으로).
두 제안은 바로 이 잔여를 겨눴고, 방향은 옳다. 다만 **실제로 정산을 3건 이상 쌓은 사람이 지구상에
창업자 1명뿐**이라, "30척 밀도" "정산 3/6/10개 도달 회고" 같은 상상 시나리오는 지금 지으면 안 된다.
그래서 이번에 **실제 코드로 짓는 건 S4 최소형(배 2~5척)과 인용벽(S6에 흡수) 뿐**이고, 나머지는
방향만 박제한다. 스파인(사용자 평가·점수·등급·streak 금지)은 코드 게이트로 못박는다.

## ① 채택안 (kill 판정 반영, 조건은 스펙으로 내장)

두 적대 판정 모두 **keep_with_conditions**. 근거가 코드·문서 현실 위에 정직하게 서 있고,
각 제안이 자기 위험을 자인했기 때문. 아래 4개 판정을 계획에 그대로 내장한다.

**A. 채택 (실제로 짓는 것)**
- **S4 함대 해도 — 최소형만.** 배 2~5척 규모, `created_at`(봉인일) 오름차순 정렬만.
  ChartPlate(현재 프로덕션 사용 0곳, 코드로 확인) 위에 기존 VoyageShip을 점선 항로에 배치.
  새 그림 부품 0개 — 100% 기존 잉크 자산의 합성.
- **인용벽(제안2 형태1) — 별도 컴포넌트 신설 금지, S6의 "문장만 보기" 필터로 흡수.**
  이미 shipped된 `JudgmentFrame`(코드 확인: DecisionContractCard:331 + SettlementModal:383)을
  재배치할 뿐. 별도 컴포넌트를 새로 만들면 CLAUDE.md 단일소스 위반 → 드리프트.
- **S6 항해일지 — 신규 작성** (봉인·변침·정산 이벤트 + 카운트 시간순 원장).
  `/project` 그리드 아래 접힌 보조 뷰. 새 라우트 금지.
- **제안2 형태2(첫 봉인 기념일 = "오늘로 N주째")** — 순수 경과 사실로만, 연속성 조건 절대 금지.

**B. 방향만 박제 (지금 코드 0줄 — 실렌더가 데이터를 줄 때까지 착수 금지)**
- **S4의 "30건 밀도 설계"** (가로 스크롤/월 압축/+N척 접기 임계값).
  → 30건 정산 사용자 0명. 임계값은 실제 다척 렌더가 나온 뒤 실측으로 잡는다.
- **제안2 형태3(정산의 계절 = 구간 결산)** — pull 전용으로 성질만 고정하되 이번 스코프 구현 밖.
  실제 렌더 가치는 정산 표본이 실제로 쌓인 뒤 판단.
- **"만 1년 금색 한 줄"** — 도달자 0명 → 최후순위.

**C. 판정이 잡아낸 낡은 전제 2건 — 교정 완료 (검증됨)**
- 두 제안 모두 "DecisionReplayTimeline 재사용 판정 먼저 / WakeReturn 흡수 후 삭제"를 전제했으나,
  **두 컴포넌트는 이미 제거됨** (git 커밋 `5d428ea chore(cleanup): remove dead
  WakeReturn/DecisionReplayTimeline (never wired)` 확인). → S6은 **신규 작성**으로 진행하고,
  "재사용/거취 판정 회의" 자체가 불필요하다. 스펙에서 이 두 문구를 삭제한다.
- S1~S5·S7이 이미 shipped인 것도 코드·git으로 확인 → 이 계획은 "다음 단계"만 다룬다.

**D. 회의론자의 잔여 위험 — 합성 레벨 판정 (거울 조항)**
- 개별 배 rig이 무변경이어도, **한 폭의 해도 위에 난파·표류·verified를 나란히 놓은 "구도 자체"가
  성적표로 읽힐 수 있다.** rigOf 값 보존만으로는 이 공간적 판정을 중화하지 못한다
  (honest provenance는 필요조건이지 충분조건 아님). → S4 스펙에 **코드 게이트**로 명문화(④ 참조).

## ⑥ 창업자 버튼 (자율 실행이 못 하는 것)

아래는 **사람(창업자)만 할 수 있는 결정/행동**이다. 이게 없으면 위 계획은 코드가 짜여도 검증이 반쪽이다.

1. **[가장 중요] 착수 GO 신호** — 이 계획은 "S4/S6은 다음 단계 후보(마스터 §132가 이번 실행 밖으로 defer)"를
   전제로 한다. **실사용에서 정산이 최소 몇 건 실제로 도착한 뒤** 착수하는 게 두 판정의 공통 최우선 조건.
   지금 창업자 1명(정산 4건)뿐이라도 dogfood로 함대 해도를 실렌더해 임계를 잡을 수는 있음 →
   "지금 B1~B3만 dogfood용으로 짓자" vs "실사용자 정산이 몇 건 더 올 때까지 기다리자"는 **창업자 판단**.
2. **dogfood 실관찰** — 자율 실행은 빌드/타입/테스트까지만 신뢰 가능. "함대 해도가 실제로 아름다운가,
   난파 배가 성적표로 안 읽히는가"는 **창업자 눈**으로만 최종 판정(실제 사용자가 최종 검수라는 원칙).
3. **정산의 계절/기념일 실렌더 착수 여부** — 표본이 언제 충분한지(정산 3+ 도달자가 창업자 외 몇 명 생겼는지)는
   실DB를 보는 창업자만 안다. 이 계획은 그 판단의 트리거를 자동화하지 않는다(자동화하면 곧 cron=스파인 위반).
4. **외부 공개/배포** — 이 스코프엔 없음(전부 기존 표면 내부). 새 도메인·실발송·외부 리스팅 불요.
