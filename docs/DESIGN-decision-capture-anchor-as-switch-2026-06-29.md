> 2026-06-29. 비개발자 창업자와의 긴 설계 대화 결론. seal/settle을 "일일이 부르는
> 기능"에서 "대화에 녹아 따라붙는 것"으로 옮기기 위한 전반 설계.
>
> **한 줄:** 닻(출항 전 한 줄 입장)은 단순 메모가 아니라 **이 세션을 추적·기록할지
> 켜는 스위치**다. 켜진 세션만 비용을 쓰고, 꺼진 세션도 *마지막엔 한 번* 값싸게

## 1. 배경 — 왜 이 설계가 필요한가

- **즉각 hook이 없다.** seal/settle은 본질적으로 저빈도 + 지연보상이라 "매일 손이
  가는" 기능이 아니다. (1차 정산 WakeReturn이 즉각성을 일부 보완하지만, 그것도
  "결정을 끝까지 돌린 사람"만 본다.)
- **명시 호출의 벽.** 현재 플러그인은 `/argus:sail` 등을 **사용자가 의식적으로
  불러야만** 동작한다(자동 백그라운드 포착 없음 — Explore 확인). "일일이 부르는 건
  귀찮아서 안 쓰게 된다."
- **그렇다고 전수 감시는 안 된다.** 사사건건 개입 = 거슬림(스파인 mirror clause
  위반), 모든 대화 감시 = 프라이버시/비용 문제.
- **`0 settled`는 수요 반증이 아니다.** 루프의 마지막 조각이 미완성이라 시동이 안
  걸린 것. (창업자 교정, 2026-06-29) — 이 설계가 그 마지막 조각.

핵심 긴장 셋(창업자가 직접 짚음): **귀찮음**(일일이 부르기) · **거슬림**(사사건건) ·
**프라이버시**(다 열기). 이 셋을 *동시에* 푸는 것이 설계 목표.

## 2. 토대 — seal 재정의와 정산 2개 (이미 합의)

### 2.1 seal은 "정리된 생각"이 아니라 "시간만 답할 한 줄"
- 정리된 생각/초안/할 일 = **결과물** → export(저장/slack). seal 아님.
- seal = 결과물에서 **"지금 나도 모르고, 시간이 지나야만 알 수 있는 한 문장(베팅)"**
  하나를 떼어 거는 것.
- **To-do를 seal에 묶는 것은 기각.** settle이 "예측 맞았나(배움)"에서 "할일 했나
  (생산성)"로 변질 → Todoist화 → 차별화 소멸.

### 2.2 묶기 1번 + 정산 2번 (오디세우스: 한 번 묶고, 끝에 푼다)
```
[묶기]  naive 한 줄 = 닻              흔들림 방지 + 비교 기준 (출항 전 돛대)
   │
[듣기]  AI와 대화 (세이렌=LLM)        결과물 → export
   │
[1차 정산] 닻 vs AI거친 생각          즉시·전원·공짜 = 활성화 온램프
   │       "AI가 날 어디로 끌었나"     ← WakeReturn (구현됨)
   ⋯ 시간 ⋯
[2차 정산] 베팅 vs 현실               옵트인·기간후 = moat. 1차가 2차를 판다
```
- 1차 = "AI 앞 흔들림 패턴"(빠름·전세션). 2차 = "판단 보정"(느림·건것만). 1차가 2차의
  표본을 늘린다.
- 1차 정산은 **거울만, AI 판정 0** (zero-judgment). "움직였다"는 사실, "현명해졌다"
  금지.

### 2.3 닻 질문은 이미 입장형 (안 건드림)
- webapp BindCard / plugin clarify Step 3.4: *"지금 마음은 어디로 기울어요?"*
  = 감정이 아니라 **입장**. 비교가 성립. 맞춤 예시/선택지 제공은 **닻 오염(borrowed
  rope)** = 기각.

## 3. 핵심 원리 — 닻 = 추적 스위치

> 닻을 박은 세션 = 추적 ON (조용히 따라다니며 항적을 그림).
> 닻을 안 박은 세션 = 추적 OFF (비용 0으로 비켜 있되, 마지막에 한 번만 돌아봄).

이 한 장치가 세 긴장을 동시에 푼다:

| 긴장 | 닻=스위치가 푸는 법 |
|---|---|
| 귀찮음 | 닻 박은 세션은 항적까지 자동으로 따라옴 — 다시 안 불러도 됨 |
| 거슬림 | 닻 안 박은 세션(대부분)은 침묵 — 코딩하는데 안 끼어듦 |
| 프라이버시 | 추적은 *닻을 박아 동의한 세션만*. 전수 감시 아님 |
| (+ 비용) | 닻 없으면 LLM이 거의 안 불림 — 스위치가 비용 게이트 |

## 4. 사용자 여정 (개발자로 좁히지 않는다)

플러그인 주 고객은 개발 베이스가 있는 사람이 되겠지만, 거기서 코드만 하는 게 아니다.
(창업자 본인이 비개발자로서 Claude Code류 창에서 제품 전략을 구체화 중 = 반증.)

| 여정 | 누구/무엇 | 빈도 | 결정의 순간 | 자동 포착 적합성 |
|---|---|---|---|---|
| ① 코드 결정 | 머지/롤백/마이그레이션 | 높음 | 구조화(plan·commit·PR) | 트리거 잘 맞음 |
| ② 비-코드 사고 | 개발자가 개발 밖 고민(우선순위·채용) | 중간 | 대화 속, 구조 없음 | 어려움 ← 미해결 |
| ③ 기술친화 비개발자 | 전략·GTM·설계(창업자 본인) | 세션당 다수 | 순수 대화, 구조 0 | 어려움 ← 미해결 |
| ④ 저빈도 중대결정 | 이직·창업·큰 투자 | 매우 낮음 | 본인이 의식 | 명시 호출이 자연스러움 |

**패턴:** 자동 포착 적합성 = (결정의 구조화 정도) × (빈도). 하나의 모드로 다 못 잡는다.
②③(구조 없는 사고)이 가장 어렵고, 동시에 가장 큰 미개척 사용자층.

**범용 진입점:** 직군 무관하게 공통점 하나 — *누구든 중요한 결정 앞에서 AI에게
묻는다.* **결정의 순간 = AI에 묻는 순간.** 그래서 "AI와 대화하는 창"(플러그인/웹앱)에
붙는 것이 범용 포착의 자리.

## 5. 세 가지 세션 모드

| 모드 | 언제 | 추적 | 비용 |
|---|---|---|---|
| **① 닻 ON** | 시작 시 닻 박음 | 풀 추적 — 매 턴 신호 체크, 결정 완결 시 항적·seal | 닻 있을 때만 LLM |
| **② 늦은 ON** | 닻 없이 시작 → 대화가 결정으로 깊어짐 | **자연스럽게** 닻 흐름 시작 (메타질문 X) | 1층 신호 강할 때만 |
| **③ OFF** | 닻 없고 결정 신호도 없음 | 매 턴은 안 건드림. **마지막에 1회 회고** | LLM 0, grep만 |

대부분의 세션은 ③ = 비용 거의 0.

## 6. 세션 라이프사이클 (오디세우스 3단계 → hook 매핑)

```
┌─ SessionStart (안정적) ──────────────────────────────┐
│  (a) 직전 'OFF 세션' 1회 회고 → 결정 있었으면 슬쩍 언급   │ ← "마지막 확인"
│  (b) 오늘 닻 제안 (결정 맥락일 때, 자연스럽게)           │ ← 묶기 / 스위치 ON
└───────────────────────────────────────────────────────┘
        │   세션 중 = AI와 대화                            ← 듣기
        │
┌─ 매 턴 Stop (매번 도나, 게이트로 대부분 침묵) ──────────┐
│  닻 ON 세션만:  1층 grep/git(공짜) → 2층 LLM(통과 시)    │
│                → 결정 완결되면 "항적" + seal 제안         │ ← 닿기 / 항적
│  닻 OFF 세션:   1층 grep만(공짜), 강신호 뜨면 모드②로     │
└───────────────────────────────────────────────────────┘
```

## 7. "마지막 확인"을 신뢰성 있게

- **문제:** 닻 안 박은 세션도 마지막엔 보고 싶은데, `SessionEnd` hook은 **못 믿는다**
  (터미널 닫기·크래시 시 안 돔). `Stop`은 매 턴이라 "마지막"을 모른다.
- **해법:** "마지막 확인"을 *그 세션 끝*이 아니라 **다음 세션 시작(SessionStart, 안정적)**
  에서 한다. 직전에 닻 없이 끝난 세션의 transcript를 1회 값싸게 회고 → 결정이 있었으면
  *"지난번 그거, 어떻게 됐어요?"* 로 자연스럽게 잇는다.
- **이중 안전망:** ③ 세션 도는 동안 1층 grep(공짜)이 강신호를 만나면 즉시 모드②(늦은
  닻)로. 임계를 못 넘고 끝난 세션은 다음-시작 회고가 줍는다. → 하나도 안 놓치되, 세션
  도는 동안 비용 0.

## 8. 비용 모델 (언제 LLM을 부르나)

| 단계 | LLM? | 빈도 |
|---|---|---|
| 1층 신호 (grep 키워드 + git 상태 + plan 파일 존재) | ❌ 공짜 | 매 턴 |
| 2층 판단 (걸 만한가 + 항적) | **메인 Claude 위임 — 별도 콜 0** | 닻 ON + 1층 통과 시만 |
| 다음-시작 회고 | 메인 위임 (또는 1콜) | 닻 없던 세션당 1회 |

**2층의 토큰 최적 구현 (중요):** 2층을 *별도 API 콜*로 만들지 않는다. hook(공짜
grep)이 신호를 잡으면 `additionalContext`로 **메인 Claude에게 위임** — 메인은 이미
대화 맥락을 들고 있으므로 추가 입력 토큰 0, 별도 콜 0. "백그라운드가 토큰 많이 쓴다"는
불평의 원천을 아예 제거한다. 닻을 안 박으면 1층 grep만 돌고 위임도 안 일어난다.
**스위치가 곧 비용 게이트.**

## 9. UX 원칙 — 메타질문 금지, 대화에 녹임

**"결정 같은데 닻 박을래요?" 같은 팝업/메타질문을 띄우지 않는다.** Claude의 *말 속에
자연스럽게* 녹인다.

```
❌ [시스템] 결정이 감지되었습니다. 닻을 기록하시겠어요? [네/아니오]

✅ Claude: "...두 방향이 있는데요. 듣기 전에, 지금은 어느 쪽으로 더 기울어요?
            한 줄이면 돼요. (나중에 답이랑 맞춰보면 재밌거든요.)"
```

- 항적도 "기록을 비교합니다"가 아니라 *"아까 A 쪽이라 하셨는데, 지금 B로 가시네요"*
  처럼 대화의 일부로.
- 사용자는 "기능을 쓴다"는 느낌 없이, 그냥 대화하는데 닻과 항적이 따라붙는다.
- "늦은 닻"(모드②)도 *"닻 박을래요?"* 가 아니라 자연스러운 시작으로(창업자 지시).

## 10. 데이터 / 프라이버시

- **저장:** 결정 한 줄(닻 → 항적 lean_after → 베팅 predicate) + 확인일. ledger,
  **로컬**(`.argus/`, gitignore).
- **저장 안 함:** 대화 원문. (Claude Code가 이미 보유; Argus는 *증류물만* 남김.)
- **감시 아님:** 추적은 닻을 박아 *동의한 세션만*. 닻 없으면 마지막 1회 회고가 전부.
- LLM 판단(2층)은 별도 빠른-모델 API 1콜로 transcript 일부를 보지만, Claude Code가
  *이미* 그 대화를 모델에 보낸다 → 추가 유출 없음.

## 11. 스파인 정합 (어기면 안 되는 선)

- 닻은 **AI가 채우지 않음**(borrowed rope 금지) — 늦은 닻도 사용자 말로만.
- skip은 항상 1탭, 무손실 (forced-typing gate 금지).
- 항적에 **AI 판정 0** (거울만 — "움직였다"는 사실, "잘했다/AI 덕분" 금지).
- 무신호 세션엔 **침묵** (over-fire = mirror clause 위반).

## 12. 기술 사실 — hook 메커니즘 (구현 제약, claude-code-guide 확인)

| hook | 발동 | 신뢰성 | 비고 |
|---|---|---|---|
| **Stop** | **매 응답(턴)마다** (세션 끝 아님) | 항상 | transcript_path 받음 |
| **SessionEnd** | /clear·logout 등 | ⚠️ 터미널 닫기·크래시 시 안 돔 | reason: clear/resume/logout/… |
| **SessionStart** | 새로/resume/clear/compact | ✅ 안정적 | source로 필터 가능 |

- **모든 hook이 transcript(JSONL 전체 대화)에 접근** 가능(stdin의 transcript_path).
- **hook은 LLM을 부를 수 있다:** `type:"prompt"`(단발) / `type:"agent"`(Read·Grep
  서브에이전트). 단 별도 빠른-모델 API 콜 = 비용 → 1층 값싼 필터가 필수.
- **hook은 skill/슬래시명령을 직접 못 부른다.** 대신 `additionalContext`로 Claude에게
  귀띔 → Claude가 제안/실행 (`SessionStart`·`UserPromptSubmit`·`Stop`에서 가능). 약간의
  간접성이 있다(완전 자동 아님).
- 권장 패턴: Stop hook 2층 — 값싼 휴리스틱(grep/git/plan 파일) → 통과 시 LLM 판단 →
  감지되면 additionalContext로 자연스러운 닻/항적 흐름 트리거.

## 12.5 신호 설계 (선별 = 제품의 숨은 심장)

### 신호는 두 종류 — 시작(열림) vs 완결(닫힘)
"결정 신호"를 한 덩어리로 보면 "언제 닻, 언제 항적"이 엉킨다. 둘로 나눈다:

| 신호 | 언제 | 트리거 | = |
|---|---|---|---|
| **시작 신호** | 갈림·저울질이 시작될 때 | 닻 제안 (before) | 결정이 *열릴* 때 |
| **완결 신호** | 답 듣고 마음이 정해질 때 | 항적 + seal (after) | 결정이 *닫힐* 때 |

### 기준 = "결정인가?"가 아니라 "걸 만한 결정인가?"
모든 결정이 아니라 **시간이 지나야 현실이 답할·사소하지 않은** 결정만(§2.1 seal 정의).
2층 분업:
```
1층 (공짜·결정론):  "결정의 징후가 있나?"  ← 어휘·구조, 재현율 우선(헐겁게)
        ↓ 걸리면만
2층 (LLM 1콜):      "이거 걸 만한가?"       ← 시간이 답할·비사소, 정밀도
```
1층이 0이면 LLM 안 불림 = 비용 0.

### 1층 신호 구체 목록
| 종류 | 시작 신호 (→닻) | 완결 신호 (→항적) |
|---|---|---|
| **언어** | "할까/말까", "vs", "둘 중", "고민", "어느 쪽", "should I", "or" | "그럼 X로", "좋아 가자", "정했어", "let's go with" |
| **구조** | ExitPlanMode 진입, 새 브랜치, plan 파일 생성 | git commit, plan 승인, PR 생성 |
| **형태** | 한 주제로 길게 저울질(N턴↑) | 저울질이 한 방향으로 수렴 |

②③(비구조 사고)는 **언어 신호만** 작동 → 거기선 2층 LLM이 더 중요(코드 신호 없음).

### 피로 관리
닻/항적 제안은 **세션당 1회**, 거절 시 그 세션 다시 안 물음(helm "같은 세션 두 번
제안 금지"와 동일). 닻 제안은 skip 1탭 무손실이라 false positive 비용은 "약간 거슬림"뿐.

### 진입점 정정 — SessionStart 단독은 맥락 0
세션 시작 순간엔 transcript가 비어 사용자 의도를 모른다. 그래서:
- **SessionStart hook** = 스위치 준비 + *직전 세션 회고*만 (닻 제안 X)
- **첫 UserPromptSubmit** = 1층 시작 신호 체크 → 결정 맥락이면 자연스러운 닻 흐름
→ "SessionStart 닻"은 실제로 **"세션 초반 첫 결정 프롬프트에서 닻"**이다.

## 13. 구현 순서 (싸고 안정적인 것부터, 각 단계 dogfood 검증)

1. **닻 진입** — 스위치의 시작점. *(여기부터)*
   - SessionStart hook: 직전 OFF 세션 회고 + 스위치 준비 (닻 제안은 아직).
   - **첫 UserPromptSubmit**: 1층 시작 신호 → 결정 맥락이면 자연스럽게 닻(before) 제안.
2. **Stop 1층 신호** (닻 ON 세션, grep 어휘 + git 상태) — 공짜.
3. **Stop 2층 항적** (1층 완결 신호 통과 시 LLM 1콜) — 비용 게이트, 결정 닫히면 항적 + seal.
4. **다음-시작 회고** (닻 없던 세션 마지막 확인) — 놓침 방지. → `recall-signal.js`
   (SessionStart): 직전 OFF 세션 transcript tail에 완결 신호가 있으면 메인 Claude에게
   "지난번 그거 어떻게 됐어요?"를 귀띔. readdir + tail grep, LLM 0, 직전 세션당 1회.
5. **늦은 닻** — 별도 코드 불필요(anchor-signal에 내재): 세션당 1회 마커이므로, 첫
   프롬프트에 신호가 없으면 마커를 안 쓰고 → 이후 어느 프롬프트의 첫 시작 신호에서 제안.

**구현 메모:** 1층 grep 패턴·transcript 읽기는 `scripts/lib/decision-signals.js` 단일
소스(anchor/wake/recall 공유, CLAUDE.md "두 번째 위치엔 추출"). hook은 출력 잘림 방지로
`process.exit()`를 두지 않는다(자연 종료가 stdout flush 보장). 경로 주의: hook input의
transcript_path/CLAUDE_CONFIG_DIR은 실전에서 OS 절대경로(Windows면 `C:\...`)라 node가
바로 읽지만, git-bash 테스트는 `/tmp`를 stdin JSON으로 주면 win-node가 못 읽으니
`cygpath -m`로 변환해 검증한다.

각 단계는 webapp ↔ plugin 형태 통일 유지(메모리: drift 경고). lean_after {text,changed}
스키마 일치, ledger `wake` 이벤트 형태 일치.

## 14. 열린 질문 / 리스크

- ~~1층 신호 정의~~ → **해소됨(§12.5):** 시작/완결 2종, "걸 만한가" 기준, 1층 목록,
  첫 UserPromptSubmit 진입점. 남은 미세조정은 구현 중 dogfood로.
- **2층 LLM 프롬프트 정밀도:** "걸 만한 결정인가"를 판단하는 프롬프트가 ②③(비구조
  사고)에서 얼마나 정확한가 — 실측 필요(구현 후).
- **늦은 닻의 자연스러움:** 메타질문 없이 "자연 시작"을 어떻게 일관되게? 카피·트리거
  설계 필요.
- **검증의 본질:** 플러그인 자기채점은 시뮬 — 실사용자(우선 창업자 dogfood)가 최종
  검증. "내세울 기능인가 / 계속 쓸 기능인가"는 한 바퀴(seal→settle)를 실제로 돌아야
  답난다.
- **차별화 vs 리텐션 구분:** seal은 *내세울 차별화*로는 진짜(LLM 기억도 못 먹는 유일
  자산)지만 *매일 쓰는 데일리 기능*으로는 구조적으로 아님. 리텐션은 seal 앞단
  (자주 쓰는 orientation/생성)에서, seal은 "이 도구는 다르다"의 증거로. seal을 "매일
  쓰는 결정 저널"로 *약속하지 말 것*.

## 15. 용어

- **닻 (anchor / rope):** 출항 전(AI 듣기 전) 사용자의 한 줄 입장. `user_lean`. 이제
  **추적 스위치** 역할도.
- **항적 (wake):** 닻 vs 들은 후 입장. 1차 정산. `lean_after {text, changed}`.
- **베팅 (predicate):** 시간만 답할 한 문장. 2차 정산 대상.
- **1차 정산:** 생각↔생각(즉시). **2차 정산:** 생각↔현실(기간 후).
- **1층/2층:** 값싼 결정론 신호(grep/git) / LLM 판단.
