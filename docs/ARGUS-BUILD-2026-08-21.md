# 아르고스 시공 계획 — 무엇을 짓고, 무엇을 살리고, 무엇을 버리나 (2026-08-21)

> 기획서(`ARGUS-PLAN-2026-08-21-V5.md`)는 **무엇을 만들지**를 정했다. 이 문서는
> **어떻게 만들지**를 정한다. 코드는 한 줄도 안 짠다 — 기획서 머리의 `adopted`가
> 비어 있는 동안은 시공 0이 규칙이다.
>
> **이 문서를 쓴 이유**: 기획서가 기존 코드를 *"박물관(동결) — 재사용하는 것은
> 기계가 아니라 배운 것"*이라 한 줄로 처분했는데, **실측해 보니 그게 과했다.**
> 안 보고 처분하면 이미 있는 것을 다시 짓거나, 살아 있는 것을 지운다.

### §1-b. 배선을 끝까지 따라가 보니 — 한 곳이 끊겨 있다

**첫 보고는 틀렸다.** 파일 이름·줄 수·맨 위 주석만 보고 "있다"고 적었다. 주석은
*무엇을 하려 했나*이지 *무엇을 하나*가 아니다. 실제로 돌리고 따라간 결과:

**돌려서 확인한 것**: `npm run build` 통과 · `npm test` **143파일 1,297개 전부 통과**.
부품은 실재하고 테스트도 산다.

**따라가 보니 끊긴 곳**:

```
소비 쪽   check_in 도구 → drainCaptureOnCheckIn → capture-runtime.ts:65
          → runHarvestSweep                                        ✅ 이어져 있다
생산 쪽   capture-scan 명령 (argus-mcp/src/index.ts:17)             ✅ 있다
          ← 부르는 것: argus-plugin-v2/scripts/decision-ledger.js:750 ✅ 있다
            ← 부르는 것: **훅이 아니라 스킬 문서**
               (skills/review/pipeline.md · clarify.md)            ⚠ 여기가 문제
```

플러그인 훅은 12개 걸려 있는데(SessionStart 3 · UserPromptSubmit 3 · PreToolUse 2 ·
PostToolUse 2 · Stop 2) **그중 `decision-ledger.js`를 부르는 것이 하나도 없다.**
부르는 것은 스킬 마크다운이고, 그건 **AI가 그 문서를 읽고 셸 명령을 칠 때만 돈다.**

이 저장소는 이 패턴을 이미 알고 이름까지 붙여 뒀다 — `ARGUS-CORE.md` §6.2의
"참조 0의 아홉 이유" 중 다섯째: *"스킬 마크다운이 셸로 호출."* 죽은 코드가
아니라는 뜻이지만, **자동으로 돈다는 뜻도 아니다.**

**그래서 판단이 갈린다: 부품은 재사용하고, 배선은 재사용하지 않는다.**
지금 배선은 CLAUDE.md가 금지한 모양이다 — *"라우팅·순서는 결정론 구조가 갖고,
LLM은 셀 안의 창의 작업만."* AI가 그날 그 문서를 안 읽으면 수집이 안 된다.
→ **N6(아래)이 새로 생긴다.**

**세 번째 존을 빠뜨렸다**: 첫 보고는 `argus-mcp`와 `src/` 둘만 셌는데,
`argus-plugin-v2`가 **JS 6,674줄에 훅 12개**로 따로 있다. 훅 표면은 전부 여기다.

> **이 발견이 계획을 바꾼다.** 기획서 §4.2의 *"기존 커널 코드는 박물관(동결) —
> 재사용하는 것은 기계가 아니라 배운 것이다"*는 **틀렸다.** 배운 것만이 아니라
> **기계도 상당 부분 그대로 쓸 수 있다.** 다만 조건이 하나 있고, 그게 §3이다.

## §3. 진짜 갈림길은 하나뿐이다 — 결정을 어디에 저장하나

나머지 모든 판단이 여기에 딸려 온다.

### 두 안

| | **A안 — 마크다운 파일이 진실** (기획서 현행) | **B안 — 기록 파일이 진실, 마크다운은 사본** |
|---|---|---|
| 결정 1건 | `decisions/D-0012.md` 한 파일 | `~/.argus/.../ledger.jsonl`의 사건들 |
| 사람이 읽는 것 | 그 파일 | `decisions/D-0012.md` (기계가 만들어 준 사본) |
| 편집하면 | **법이 바뀐다** | **아무 일도 안 일어난다** (다음에 덮어써짐) |
| git | 역사 그 자체 | 사본의 역사 |
| 기존 코드 | 대부분 못 씀 | **8,296 + 4,572줄을 그대로 씀** |

### 왜 이게 그냥 취향 문제가 아닌가

**A안은 우리가 이미 찾아낸 결함을 되살린다.**

기획서 §4.10에 이렇게 적혀 있다 — *"평문이 서명 대리 불가를 무력화한다.
에이전트가 그냥 파일을 쓰면 되는 세계에서는 무의미하다."* 이건 우리가 스스로
공격해서 찾은 구멍이고, 처방으로 서명 봉인(키·해시)을 붙이기로 했다.

**B안에서는 그 구멍이 애초에 안 생긴다.** 확인은 도구를 거쳐야만 기록에 남고,
마크다운은 기계가 만든 사본이라 **AI가 그 파일을 아무리 고쳐도 법이 안 바뀐다.**
봉인 장치가 필요 없어지는 게 아니라, **없어도 반쯤 막힌다.**

그리고 이미 `v2/ledger.ts` 주석에 이 설계가 적혀 있다 — *"worktree의 .argus/에는
projection만 산다."* 우리가 예전에 같은 답에 도달했던 것이다.

### 무엇을 잃나 (정직하게)

- **"에디터가 곧 편집 도구"라는 그림을 잃는다.** 파일을 고쳐서 법을 바꾸는 건
  못 한다. 대신 `dec amend` 같은 명령을 써야 한다.
- **기획서 문장 하나를 고쳐야 한다** — §4.2의 *"git이 역사·동기화·병합을
  담당한다"* → *"git은 사람이 읽는 사본의 역사를 담당하고, 진실은 기록 파일이다."*
- **여러 대에서 쓸 때 동기화가 git 공짜가 아니다.** 다만 이것도 이미 있다
  (`v2/outbox.ts` + `tools/sync.ts` 400줄).

### 권고

**B안.** 근거 셋:
1. 이미 있는 **12,868줄을 살린다** (그중 상당수가 테스트까지 딸려 있다)
2. 우리가 찾은 결함(파일을 쓰면 서명이 된다)이 **구조적으로 안 생긴다**
3. 잃는 것("에디터로 편집")은 **시뮬 20명 중 아무도 요구하지 않았다** —
   되짚어 읽는 건 다들 원했지만 고치는 건 명령으로 했다

→ **창업자 판정 10번**으로 올린다. 이건 AI가 정할 수 있는 종류가 아니다.

**"읽고 다시 판정"이 넷이나 되는 게 정직한 상태다.** 안 읽고 처분하면 이

뜻이 아니라 아홉 가지 이유 중 하나라는 뜻*(`docs/ARGUS-CORE.md` §6.2).

## §5. 순서 — 무엇부터, 그리고 "돌아간다"의 뜻

각 단계마다 **눈으로 볼 수 있는 증거**를 정의한다. 증거가 없으면 다음으로 안 간다.

| 순서 | 짓는 것 | "됐다"의 정의 |
|---|---|---|
| **0** | 기록 쓰는 코드를 **하나로 합친다** (셋이다 — `lib`·`v2`·플러그인) | 기록에 쓰는 경로가 하나다. 다른 경로를 부르면 테스트가 빨간불 |
| **0-b** | **N6 훅** — 대화 수집이 자동으로 돈다 | 세션을 끝내고 아무것도 안 했는데 큐에 항목이 쌓인다. **이게 되기 전에는 나머지가 다 "손으로 쳐야 도는 기능"이다** |
| **1** | 새 사건 종류 더하기 (확인·개정·폐지·이탈…) | 사건을 쓰고 되읽어 같은 상태가 나온다 |
| **2** | **N3 규칙 파일 읽기** | 이 저장소의 CLAUDE.md에서 조항 40개 안팎이 후보로 나온다 |
| **3** | **N1 감시 규칙 만들기** | 조항 하나가 "어떤 파일·어떤 말"로 바뀌고, **못 잡는 것도 같이** 나온다 |
| **4** | **N2 지난 기록에 대입** | *"이 규칙이 있었으면 지난 30일에 N번 걸렸다"*와 그 장면이 나온다. **여기까지가 첫날 60초다** |
| **5** | 확인 한 타 + 근거 문장 저장 | 확인하면 파일이 생기고, **그때 내가 쓴 문장이 그 안에 있다** |
| **6** | 세션 시작 때 보여주기 | 새 세션을 열면 확인한 규칙이 보인다. **다른 프로젝트 규칙은 안 섞인다** |
| **7** | 어긋나면 알려주기 | 규칙에 걸리는 작업을 하면 한 줄이 뜨고, **[잘못 잡았어요]가 눌린다** |
| **8** | 다시 묻기 + 닫기 | 날짜가 되면 물어오고, **그때 내가 쓴 문장을 보여준 뒤** 한 글자로 닫힌다 |
| **9** | **N4 차단 훅** · **N5 규칙 파일 내보내기** | 훅이 실제로 막고, 내보낸 파일을 손으로 고치면 알아챈다 |

**4번까지가 1주차다.** 그 지점에서 이미 사람이 값을 본다 — 아직 아무것도 확인
안 했는데도 *"내 규칙 중 몇 개가 지난 달에 안 지켜졌다"*를 보여주니까.

**5~8번이 2주차다.** 여기까지 와야 한 바퀴가 돈다.

**9번은 자를 수 있다.** 기획서의 자르기 금지선 다섯에 안 들어간다.

## §6. 이 저장소에서만 걸리는 함정 (미리 적어둔다)

1. **CI의 `check` 잡이 로컬보다 넓다.** `npm test`는 덮개율을 안 재는데 CI는 잰다.
   테스트 없는 큰 파일을 더하면 **로컬 초록 · CI 빨강**이 난다. 새 파일마다
   테스트를 같이 쓴다.
2. **MIT 존과 앱 존을 한 PR에 섞으면 막힌다** (`zone-purity` 검사). 새 코드는
   거의 다 `argus-mcp/`(MIT)라 대부분 한 존이지만, 화면 쪽을 건드리는 순간
   PR을 갈라야 한다.
3. **MIT 존을 고치면 로컬 `npm test`가 아무것도 검증 안 한다** — 자체 검사기를
   갖고 CI에서만 돈다. 로컬에서 초록 봤다고 안심하면 안 된다.
4. **잠금 규율을 깨면 조용히 데이터가 깨진다.** `lock → 되읽기 → 전이 검사 →
   쓰기 → 잠금 해제`가 범위이고, 영수증·내보내기는 **잠금 밖**이다. 지금 코드가
   그렇게 돼 있고 이유가 주석에 적혀 있다.
5. **날짜 계산을 직접 하지 않는다.** `resolve-today.ts`가 "기한은 오늘보다 커야
   한다"를 강제한다. 이걸 우회하면 하루 짜리 왕복이 이틀이 된다 (이미 한 번 겪음).
6. **인용문은 바이트로 대조한다.** `harvest.ts`가 이미 그렇게 한다 — 인용이
   원본에 진짜 그대로 있는지 확인하고, 없으면 버린다. **이 검사를 끄면 제품이
   지어낸 인용을 사용자에게 보여주게 된다.**
7. **새 필드를 더하면 따라와야 하는 것들이 있다.** 이 저장소는 그걸 규약으로
   갖고 있다(CLAUDE.md의 필드 추가 점검표·스키마 동기화). 새 사건 종류를
   더할 때 같은 규율을 따른다.

## §7. 안 만들 것 (명시)

기획서의 "안 만든다" 목록에 더해, **시공 단계에서 손이 가기 쉬운 것들**:

- **규칙 파일 뿌리기(fan-out) 도구** — 무료 도구가 여덟 개 넘는다. 내보내기와
  호환만 한다.
- **새 화면(웹·앱)** — 기획서 판정 8번이 열려 있다. 관문 2 전까지 안 짓는다.
- **크론·알림 재연결** — §4의 처분 그대로.
- **런타임에 모델 부르기** — 규칙을 만들 때(사람이 확인하는 순간)만 부른다.
  걸렸는지 판정하는 자리에 모델을 넣으면 되돌릴 수 없다.
- **임베딩·그래프 검색** — 기획서가 이미 금지했다. 시공에서 다시 유혹이 온다.
- **"전제" 개념 되살리기** — 808줄이 있어서 쓰고 싶어지지만, 새 기획에 그
  개념이 없다. 잠근다.

## §8. 창업자가 정할 것 — 하나 늘었다

**판정 10 (신규): 결정을 어디에 저장하나 — A안(마크다운이 진실) vs B안(기록이
진실, 마크다운은 사본).**

- **A안**: 기획서 현행. 에디터로 고칠 수 있다. **기존 코드 대부분을 못 쓴다.**
  그리고 "파일을 쓰면 서명이 된다"는 구멍을 봉인 장치로 따로 막아야 한다.
- **B안**: 기존 12,868줄을 살린다. 그 구멍이 구조적으로 안 생긴다. 대신
  **에디터로 못 고치고**, 기획서 §4.2 문장 하나를 고쳐야 한다.
- **권고: B안.** 잃는 것을 시뮬 20명 중 아무도 요구하지 않았다.

**이 판정이 §4의 처분표 절반과 §5의 순서 0~1번을 좌우한다.** 서명(`adopted`)과
같이 정해 주시면 시공이 첫날부터 안 흔들린다.

---

**상태**: 기획서 `adopted`가 비어 있는 동안 이 문서도 초안이다. 시공은 서명
뒤에만 시작하고, 이 문서의 §5 순서는 그때 작업 목록이 된다.
