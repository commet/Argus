## 0. 범위와 우선순위 (제일 중요한 것부터)

친구가 반짝인 비전 = "결정 기록을 저장하고, 전제/결론을 팔로업하다 변하면 alert,
미결정은 주기적으로 다시 고민하게, 패턴을 쌓아 비서처럼." 실측 결과 엔진은 대부분
있으나 **네 곳이 부실**하다. 중요도 순:

| # | 메커니즘 | 왜 1순위인가 | 현재 상태 |
|---|---|---|---|
| **M1** | **감지·알림 파이프라인** | 이게 없으면 나머지가 다 죽은 기능. "필요할 때 알림"의 배관 | 반쪽 (in-session pull만, 배경 push 없음) |
| **M2** | **drift materiality 규칙** | 잘못 잡으면 "중요한 변화를 놓침" = 신뢰 붕괴 | 부실 (전역 10% 고정 — 단계·경계·부호 못 잡음) |
| **M3** | **open_question 주기 재고** | 친구 포인트의 빠진 절반 | 미구현 (nudge에 안 뜸) |
| **M4** | **언어 감지·현지화** | 체감 즉각, 저위험. 다만 신뢰의 문제는 아님 | 부실 (config-only + 6도구 영어 잔존) |

**바인딩 제약 (모든 M에 적용):**
- **스파인**: "사실이 변했나"(기계적·전제정의)와 "결정을 다시 볼까"(사용자 몫)를 항상 분리.
  어떤 알림도 평결·점수·지시("~해라") 금지. handle 반환만.
- **절제**: 기본은 침묵. 중요한 변화·정한 날에만 발화. 빈도 상한 + "그만 보기" 탈출구.
- **정직 provenance**: 감지된 값의 출처(url/user/host-research) 항상 기록. 모델 추측을 사실로 위장 금지.
- **자연스러움**: 질문은 폼이 아니라 흐름의 일부로 (봉인 때 자연스럽게 1개씩). 파이프라인이
  깨지거나 어색하면 실패.
- **배경 신뢰성**: stdio MCP는 스스로 못 깨어난다 → 배경 알림은 반드시 다른 채널과 합작.

## 1. M1 — 감지·알림 파이프라인 (심장)

문제: 전제 "기준금리 3.5%"가 변했는지 알려면 누군가 (a) **현재값을 알아내고** (b) **규칙과
대조**하고 (c) **사용자가 안 볼 때도 전달**해야 한다. 현재 argus는 (b)만 있고 (a)는 host가
매번 손으로 넣어야 하며 (c)는 없다.

### 1.1 감지 방법 (기술적 — 값을 어떻게 알아내나)

| 방법 | 적용 | 정밀도 | 인프라 |
|---|---|---|---|
| **A. Host/LLM 웹리서치** | 트리거 시 LLM이 각 외부 전제의 현재값을 검색해 recheck 호출 | 중(출처 태깅 필수) | 0 (오늘 가능) |
| **B. 사용자 입력** | 사용자가 알아채고 말함 | 사용자 의존 | 0 |
| **C. 구조화 API** (금리=중앙은행, 가격=금융API) | 정형 사실 | 높음 | 도메인별 연동 |
| **D. 페이지 변경감지** (changedetection.io류·RSS·webhook) | 특정 URL 사실 | 중 | 서비스 연동 |

**결정:** v1은 **A(LLM 리서치)를 정본**으로 — 인프라 0, 어떤 전제든 커버. 단 **provenance
필수**(source=url+citation 또는 host_reported로 정직 기록, 이미 recheck에 있음). C/D는
고빈도·정형 전제(금리·환율)에서 v2 정밀화 옵션으로 박제. **모델이 값을 지어내는 것은 금지** —
반드시 검색 결과나 사용자 값에 근거.

### 1.2 트리거 — 언제 재확인하나 (cadence & 기준)

각 `external + load_bearing` 전제에 **recheck cadence**를 부여(현재 코드도 "7일 뒤 재확인
제안"이 있음 — 이를 정식 필드로). 기준:

- **변동성 기반 기본값**: 고변동(금리·가격·경쟁사)=7~14일, 중간(규제·인사)=30~90일,
  저변동(장기구조)=180일+. 모델 제안 + 사용자 조정.
- **결정 지평 연동**: check_by가 가까우면 cadence 촘촘히, 멀면 성기게.
- cadence는 **재확인 due 날짜**를 만들 뿐, 값을 안 가져온다 → check_in이 "P1 재확인 차례"로
  nudge(실측 확인됨) → 사용자 engage 시 host가 리서치(1.1-A).

### 1.3 알림 채널 — 안 볼 때도 전달 (배경 신뢰성)

**정직한 구조적 사실: stdio MCP 서버는 스스로 못 깨어난다.** 따라서 배경 알림은 **이중
파이프라인**으로, 단일 원천(ledger + due 날짜)에서:

```
                    ┌─ 단일 원천: ledger(전제·cadence·due 날짜) ─┐
   교차세션 배경 push │                                          │ 세션 내 pull/ambient
   ─────────────────┤                                          ├──────────────────
   웹앱 cron + 이메일 │  "P1(기준금리) 재확인할 때 —              │  아무 argus 도구 호출 시
   (settle 리마인더    │   지금 4.0%인지 확인해보실래요?"          │  ambient 한 줄:
    인프라 재사용,     │                                          │  "그나저나 재확인 2건·
    이미 존재)        │  drift 확인 시:                          │   미결 질문 1건"
                    │  "결정 X의 지반이 움직였어요 —            │
                    │   금리가 4.0% 선을 넘음. 다시 볼래요?"     │
                    └──────────────────────────────────────────┘
```

- **웹앱 cron(교차세션)**: 이미 있는 settle 리마인더 크론을 **전제-재확인-due**와
  **open_question-재고-due**로 확장. 이메일/텔레그램으로. = 진짜 "안 볼 때 알림."
- **MCP ambient(세션 내)**: 아무 도구 호출 시 응답 끝에 due 요약 한 줄(이미 check_in엔 있음 →
  seal/recall/settle 응답에도 얹어 "잊혀지지 않게"). 강요 아님, 사실 한 줄.
- 둘 다 **같은 due 계산**(드리프트 방지) + **빈도 상한**(리마인더 3회 상한·mute 재사용).

### 1.4 알림 발화 기준 (언제 시끄럽고 언제 조용한가)

| 종류 | 발화 조건 | 톤 | 상한 |
|---|---|---|---|
| 재확인 due nudge | cadence 도래 | 낮음, 사실 | 상한+mute |
| **drift ALERT** | recheck가 **규칙상 material drift** 판정(M2) | 높음, 그러나 handle | 즉시 1회, 중복 안 함 |
| open_question 재고 | cadence 도래 | 낮음, 젠틀 | 상한+mute |
| settle due | check_by 도래 | 중, 닻거울 | 상한(기존) |

**침묵이 기본.** material 아니면 baseline만 갱신하고 조용. 정한 날/실제 변화에만 발화.

## 2. M2 — drift materiality 규칙 (전역 % 폐기)

핵심 전환: **"숫자가 얼마 움직였나"가 아니라 "이 결정에 중요한 변화인가."** 중요도는 recheck
때 전역 상수가 아니라 **봉인 때 그 전제에 붙여 정의**한다.

### 2.1 규칙 taxonomy (전제별로 하나 이상 선택)

| 규칙 | material 조건 | 적합 예 |
|---|---|---|
| `threshold` | 값이 선 X를 넘음/미달 | "금리 4.0% 미만이면 OK" → 4.0 교차 = material |
| `step` | 단계 크기 S의 N칸 이상 이동 | 정책금리(25bp), 신용등급 |
| `delta` | 절대 변화 ≥ D | "재고 100개 이상 감소" |
| `relative` | 상대 변화 ≥ P% | 매출·트래픽 (scale-free) |
| `direction` | 부호 전환 / 0 교차 | 흑자↔적자, 성장률 ±  (opt-in만!) |
| `band` | [lo, hi] 이탈 | "환율 1300~1400 유지" |

### 2.2 사용자 예시로 검증 (4.3 → 4.0, 정책 한 단계)

- 전역 10%: 0.3/4.3 = **6.98% → 놓침** ❌ (현재 버그)
- `step`(S=0.25 또는 0.3): 1칸 이동 = **material** ✅
- `threshold`(4.0 선): 정확히 4.0 도달 = **material** ✅
- `direction`: 부호 안 바뀜 → 무시(옳음, 이 전제엔 부호 무의미)

→ 규칙을 전제에 붙이면 같은 사건이 **의미 있게** 잡힌다.

### 2.3 기본값(사용자가 규칙 미지정 시)

똑똑한 복합 휴리스틱 + 정직 고지:
1. **부호 전환은 항상 material** (단, 0이 의미 없는 양은 사용자가 끌 수 있음)
2. `relative ≥ 10% AND absolute ≥ 노이즈바닥` (0 근처 폭발 방지)
3. load_bearing인데 규칙 없으면 → 응답에 **"휴리스틱 — 규칙을 정해두면 더 정확해요"**
   + 봉인 때 규칙 1개 제안(모델 제안, 사용자 확인).

### 2.4 스파인 분리 (필수)

`recheck`는 **"material 하게 변했다"**(사실 판정 + 규칙)까지만. **"그래서 결정을 뒤집어라"는
절대 안 함** — handle 반환("다시 볼지는 당신 몫"). 규칙 자체도 사용자/전제가 정한 것이지
모델이 사용자를 평가하는 게 아님. → 스파인 무접촉 확인.

### 2.5 엣지 (숫자만도 많다 — 전수 스트레스 필요)

near-zero 폭발 · 단위 혼동(%p vs %) · 반올림 노이즈 · 비단조(왔다갔다) · 결측/추정값 ·
복수 전제 동시 이동 · 단계 크기 자체가 바뀜 · 통화/인플레 보정 · "값"이 범주형(등급 A→B).
→ **§8의 적대 스트레스 대상.**

## 3. M3 — open_question 주기 재고

미결정(`open_question`)이 check_in due에 안 뜨는 갭(실측). 설계:

- 각 open_question에 **재고 cadence**(기본 14~30일, 조정 가능).
- check_in/ambient/cron이 재고 due를 사실로 surface:
  **"N일 전 미결로 남긴 질문: '지분 구조 어떻게 나눌지'. 지금 답할 수 있나요, 아직 열려있나요?"**
- handle 3개: `resolve`(사용자 종결) · `still_open`(cadence 재설정, 조르지 않음) · `mute`.
- **강요 금지·상한 있음.** "미결로 두는 것"도 정당한 선택 — 절제.

## 4. M4 — 언어 감지·현지화

- **감지 체인**: `명시적 config > 입력 텍스트 감지 > 환경(LANG/Intl) > en`.
  입력 텍스트 감지 = 성숙 라이브러리(`CLD`/`tinyld`/`eld`) 중 1개, 짧은 문장 정확도 우선.
  (MCP 표준에 locale 규약 없음·로컬 stdio라 IP 없음 → 텍스트 감지가 정답. 검색 확인됨.)
- **현지화 잔여**: `open_decision·seal·settle·recheck·amend·dismiss` happy-path 한 줄을
  `surfaces.ts` 사전으로. **en 바이트 보존 + ko 추가**(185 테스트 보호). before 기준선 =
  dogfood 코퍼스의 EN_SURFACE 카운트.
- **주의**: 감지가 틀릴 때 escape(사용자가 명시 override) 항상 유지.

## 6. 자연스러움 (바인딩 제약의 구체화)

- 봉인 흐름에서 질문은 **한 번에 하나씩, 필요할 때만**: load_bearing 전제를 이름 붙일 때만
  "여기서 어떤 움직임이 중요해요?"(규칙) + "얼마나 자주 확인할까요?"(cadence). 폼 금지.
- 미지정이어도 **막지 않음** — 똑똑한 기본값 + 정직 고지로 진행(강제 게이트 금지).
- ambient 한 줄은 **결과를 가리지 않게** 응답 맨 끝, 사실만.
- 모든 알림에 **mute/그만보기**. 미결·미확인도 정당 → 조르지 않음.

## 7. 우선순위·시퀀싱 (구현 순서)

1. **M4 언어**(저위험·즉효, 독립) — 먼저 체감. surfaces 현지화 + 감지 체인.
2. **M2 materiality 규칙** — drift의 신뢰 코어. §8 적대 스트레스 후 확정 → 구현.
3. **M1 감지·알림 파이프라인** — M2 위에 얹힘. 웹앱 cron 확장(교차세션) + MCP ambient(세션내).
4. **M3 open_question 재고** — M1 파이프라인 재사용(같은 due/cron/ambient 배관).

M1·M3는 같은 알림 배관을 공유하므로 함께 설계·구현.

## 8. 미해결 설계 질문 (합의 필요)

1. **materiality 기본 휴리스틱의 정확한 파라미터** — 노이즈바닥·relative 임계·step 자동추정
   가능성. → **적대 스트레스(다각도 케이스 전수 + 반증)로 v1 규칙표 확정** 권고.
2. cadence 기본값의 도메인 사전(금리 vs 인사 vs 구조) — 어디까지 자동 제안?
3. 웹앱 cron 확장 시 발송 채널(이메일 already·텔레그램)과 빈도 상한 통합 정책.
4. ambient 한 줄을 어느 도구까지 얹나(전부 vs seal/recall만) — 소음 vs 망각의 균형.
5. 언어 감지 라이브러리 최종 선택(CLD vs tinyld vs eld) — 번들 크기·짧은문장 정확도 실측.
6. drift ALERT가 여러 결정에 fan-out될 때(이미 작동) 알림 묶기 — N건 한 번에 vs 각각.

→ 특히 (1)은 코드보다 설계에서 끝내야 싼 항목. 합의되면 적대 스트레스 워크플로로 규칙표 확정.
