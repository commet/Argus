## R19 — 웹앱 *literal* 엔진의 드리프트 (충격)
`src/lib/progressive-prompts.ts`의 실제 `buildInitialAnalysisPrompt`를 R12와 같은 30 케이스에 부딪힘:
| | 플러그인 v2.6 (R12) | **웹앱 (R19)** |
|---|---|---|
| total harm | 11/30 | **28/30** |
| over-fire | (낮음) | **27/30** |
| over-fire on flat | 1/5 | **5/5** |
| spine 위반 | 0 | **17** |
| 가치 중앙 | 2~3 | 1.5 |

- 웹앱 엔진엔 `frame_status`(평탄 판정)·request-type(vent/validation/info)·crisis·under-fire가 **전무**(R10 grep 확인을 행동으로 재확인). 모든 입력에 "진짜 질문 재구성 + 5단계 계획 + 다음 질문 + 통찰"을 강제 → 사소/이미결정/푸념/단순질문에도 풀 기계 = over-fire 27, 그리고 가중 선택지 + "이렇게 해라" insight = 대신 판단 17.
- 위기 4건은 베이스 모델이 막음(mishandled 0) — 엔진이 억제 안 해 다행. 단 `buildOverreachPrompt`(성공-주장 부풀리기)는 별도 단계라 이번 미측정.
- **즉 웹앱은 플러그인이 고치기 *전*보다도 나쁜 상태. 드리프트가 실측으로 확정.**

## R20 — 플러그인 판단을 웹앱 엔진에 포팅 (드리프트 닫기 시작)
`buildInitialAnalysisPrompt`에 **STEP 0(분류 게이트)** 추가: vent/validation/info/crisis/flat/open 분류 → flat·non-open이면 풀 기계 건너뛰고 직답/존중/위기대응(skeleton 빈 배열, real_question=surface). + **C+**(fork 시 가중 폴·verdict-insight 금지, crux를 *양 비용 대칭*으로). = plugin clarify/sail과 정렬(명심2의 1).
- 웹앱 코드가 방어적(`skeleton: result.skeleton || []`, real_question fallback @ progressive-engine.ts:329)이라 빈 값에도 화면 안 깨짐. **vitest 1234개 전부 통과**(프롬프트 변경이 아무것도 안 깨뜨림).
- 단 이건 *프롬프트* 포팅 — 완전 정렬엔 코드 게이트(progressive-engine 분기) + 다른 프롬프트(deepening/overreach의 verdict·success-inflation)도 후속 필요.
