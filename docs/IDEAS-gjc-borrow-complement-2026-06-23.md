# 가재(gajae-code) 대조 → Argus 보완 아이디어 (2026-06-23)

> 외부 오픈소스 **gajae-code(`gjc`, 허예찬)** 를 코드/문서 레벨로 분석한 뒤,
> "여기서 Argus가 훔칠 게 있나"를 정직하게 추린 문서.
> **핵심 주의:** 아래 ①은 *새 발견이 아니다*. `PARITY-MAP-webapp-plugin-2026-06-18.md`
> §C(단일원천화 후보)·§E(재드리프트 방지)에 이미 같은 계획이 잡혀 있다. 이 문서의
> 값어치는 **(a) 외부 레퍼런스가 그 방향이 맞다고 교차검증해준다**는 것과
> **(b) ②(영수증 가시화)는 기존 계획과 결이 다른 *추가* 후보**라는 것 두 가지.
> 다른 세션이 이미 ①/②를 건드리고 있다면 **이 문서는 폐기 대상이지 중복 작업 지시가 아니다.**

---

## TL;DR (비개발자용 한 줄씩)

- 가재는 "결정 규칙을 노트 한 장에만 적고 양쪽이 그걸 같이 읽게" 만든 도구다.
  Argus는 같은 규칙을 **웹앱·플러그인 두 군데에 따로 적어놔서** 두 번 일한다.
  → **이미 고치기로 한 일**(PARITY-MAP §E). 가재는 "그 방향 맞다"는 외부 증거일 뿐.
- 가재는 "내가 한 일의 증거(영수증)"를 화면 한가운데 자랑스럽게 보여준다.
  Argus는 핵심 흐름(봉인→정산)이 **있는데 화면에 안 보여서 봉인 0건**이다.
  → **이게 진짜 추가 후보.** 새 기능이 아니라 *이미 만든 걸 보이게* 하는 일.
- tmux는 **제품 얘기가 아니라 내 책상 정리 도구.** 꼭 필요 X. 맨 아래 짧게만.

## 0. 가재에서 실제로 가져올 만한 메커니즘 (딱 2개)

분석 출처: 레포 README + `docs/codebase-overview.md` (둘 다 직접 읽음).

가재의 나머지 부품(Rust 네이티브 가속, RPC/ACP 브리지, computer-use, transport-neutral
coordinator, tmux 병렬 워커)은 **코딩 에이전트라서 필요한 것**이고 의사결정 도구인
Argus엔 무관 → **버린다.** 이식 후보는 아래 둘뿐.

| # | 가재 메커니즘 | 한 줄 | Argus 대응 통증 |
|---|---|---|---|
| ① | **Bundled-first 스킬** — 규칙을 마크다운 1소스에 박고 런타임이 읽음. "콜드스타트 커플링" 제거 | 규칙은 한 곳, 양쪽이 읽는다 | webapp↔plugin **두 벌의 뇌가 손동기화로 드리프트** |
| ② | **Receipt/evidence를 1급 산출물로** — 실행 증거를 append-only로 쌓고 operator에게 *보여줌* | 증거가 제품의 얼굴 | seal→settle 원장이 **묻혀 있어 sealed 0건** |

## ① 규칙 단일원천화 — *대부분 이미 계획됨* (보완 = 교차검증 + 미세 추가)

### 이미 있는 것 (중복 주의 — 새로 만들지 말 것)
`PARITY-MAP §C/§E`에 그대로 있다:
- §C: frame_status·density/stakes 임계값·fork-폴 규칙·CourseStatus enum·crisis taxonomy·
  계약/정산 스키마·insight 규칙 등 **~11개 공유 판단**을 "한 곳 + parity 테스트"로 묶기.
- §E.2: 선언적 코어를 `data/`로 빼서 **webapp import + plugin 참조 + CI parity 테스트**.
- 이미 닫힌 드리프트: CourseStatus·crisis taxonomy·계약 `basis`는 단일원천+가드 **완료**.

→ **즉, 가재가 보여준 "1소스 아키텍처"는 Argus가 이미 채택해 진행 중인 방향이다.**
   가재의 기여는 *"그게 맞다"는 외부 작동 레퍼런스* 한 줄이지, 새 작업 지시가 아니다.

### 가재가 *추가로* 주는 작은 힌트 (검토만, 강요 X)
1. **죽은 코드부터 살리는 순서가 맞다.** 가재는 "규칙 노트를 런타임이 *실제로 읽는다*"가
   핵심. Argus는 `judgment-gates.ts`/`crisis-gate.ts`/`request-type-classifier.ts`가
   포팅됐지만 **DEAD(미연결)** — 프롬프트 STEP 0로만 판단 (PARITY §A.1·§E.1).
   가재 대조가 강조하는 건: **1소스로 빼기 *전에* 그 코드가 라이브에서 불리는지부터.**
   안 그러면 "예쁜 공유 노트인데 아무도 안 읽는" 상태가 된다.
   (crisis-gate는 R32에서 wire됨 — 나머지 frame_status/density도 같은 처리 필요.)
2. **override 계층.** 가재는 bundled 기본값을 로컬 `.gjc/`가 덮어쓰게 둔다.
   Argus의 `data/` 단일원천도 *프로젝트별/사용자별 override*를 처음부터 설계에 넣으면,
   나중에 "이 사용자만 다른 임계값" 요구가 와도 구조를 안 깬다. (지금 당장은 불필요 →
   메모만.)

### 보완이 *안 될* 수도 있는 지점 (정직)
- webapp(TS+LLM-API)과 plugin(마크다운 SKILL)은 **런타임 공유가 없다**(probe-prompts
  하나 제외). 가재는 *한 런타임이 마크다운을 읽는* 구조라 통째로 따라 할 수 없다.
  Argus가 할 수 있는 건 "규칙을 데이터(`data/*.json|md`)로 빼서 *각자* 읽기 + CI parity"
  까지. 가재만큼 깔끔하진 않다. → **이미 PARITY가 인지한 한계. 새 정보 없음.**

## ② 결정 영수증 가시화 — *진짜 추가 후보*

### 통증 (이미 진단됨)
`finishline-probe-2026-06-18.md` + `siren-three-phase-voyage.md`:
- 엔진은 GREEN (seal→settle 루프, `projects.decision_contract` 컬럼 실재,
  `plugin_decisions`/`plugin_bearings` 테이블, founder `/admin` 대시보드 모두 있음).
- 그런데 **sealed contract 0건.** 이유 = 기능 부재가 아니라 **안 보임**.
  3-phase(묶기→듣기→닿기)가 흩어져 있어 사용자가 "정산된 영수증"을 마주치지 못한다.

### 가재가 주는 정확한 교훈
가재는 receipt를 **operator-visible 1급 산출물**로 취급한다 — "네가 한 일의 증거"가
화면 주인공이다. Argus도 똑같은 본능(원장)을 갖고 있는데 **증거를 자랑스럽게 안 꺼낸다.**

> **핵심 한 줄: 정산된 결정 영수증을 founder `/admin`이 아니라 *사용자 본인 화면의
> 주인공*으로 올려라.** 새 엔진 X. 이미 있는 원장을 *전시*하는 일.

### 구체 보완안 (작은 것부터, 각각 독립 출하 가능)
- **B1. "정산된 영수증" 카드.** 한 결정의 [봉인 시점 가정 → 확인일 → 실제 결과 → 운/실력
  basis]를 한 장으로. 정산 완료된 계약(`decision_contract` + `basis`)을 그대로 렌더.
  *이미 있는 데이터, 새 화면 하나.*
- **B2. 워크스페이스 진입점에 "내 항해 일지(정산 영수증 모음)" 라인.** 지금 원장은
  `/admin`(founder 전용)에만 보인다 → 사용자 본인이 자기 영수증을 보는 곳이 없다.
- **B3. 봉인 직후 "영수증 예약" 확인 화면.** 봉인 = 미래 영수증 발행 약속임을 그 자리에서
  보여줘야 "왜 봉인하지?"의 답이 생긴다. (siren: Phase1→2를 *진짜 게이트*로 만들라와 연결.)
- **B4. (선택) 빈 상태 카피.** 영수증 0건일 때 "아직 정산된 결정이 없어요 — 첫 결정을
  봉인하면 확인일에 영수증이 발행됩니다" 식으로 *루프 자체를 설명.*

### 스파인 점검 (CLAUDE.md Zero-Judgment Gate 통과 확인)
- 영수증은 **사용자 소유 사실의 전시**(가정·결과·basis)이지, *기계의 판정이 아니다.*
  → rule#2(미보정 tier/verdict 노출 금지) 위반 아님. **단, basis(운/실력)는 사용자가
  정산 때 고른 값**이어야 하고 기계가 사후 채점해 덮어쓰면 안 됨 (provenance honest).
- 영수증은 "verification is not a chat"(rule#3) 위반 아님 — 단발 커밋 + 정산 시점 현실.
- over-fire 위험 낮음: 전시는 사용자가 *이미 닫은* 결정의 기록이지 새 fork 제조가 아님.
  단 B3에서 "다시 생각해볼까요?" 류로 **닫은 결정을 재오픈하면 mirror-clause 위반** →
  영수증은 *기록*만, 재고(再考) 유도 카피 금지.

### 보완이 *안 될* 수도 있는 지점 (정직)
- 근본 막힘이 "안 보임"이 아니라 **앞문(로그인 게이트 db.ts:212, 이메일 가입 깨짐)**
  일 수 있음 (finishline-probe). 영수증을 예쁘게 만들어도 **봉인까지 도달하는 사용자가
  0이면 영수증도 0.** → **순서 주의: 앞문 수리 > 영수증 가시화.** 다른 세션이 앞문을
  이미 잡고 있다면 ②는 그 다음 차례. 앞문이 안 풀렸으면 ②는 헛심.

## ③ tmux — 제품 아님, 내 작업 도구 (참고만)

- 화면을 칸으로 쪼개 **webapp 세션 / plugin 세션 / 드리프트 가드 테스트**를 나란히 띄우는
  용도. 두 표면을 동시에 만질 때 "한쪽 고치고 다른 쪽 까먹음"을 시각적으로 줄여줌.
- 단, 이미 Workflow 팬아웃(R28~R50)으로 멀티에이전트를 돌리므로 **추가 가치는 작다.**
  *여러 독립 Claude Code 세션을 병렬로 눈으로 보고 싶을 때*만 의미. **필수 아님 → 패스 가능.**

## 우선순위 제안 (다른 세션과 충돌 점검 후)

1. **(이미 진행 중) ① 단일원천화** — 새로 손대지 말 것. PARITY §E가 주인. 가재는 외부 검증.
   - 단 §E.1 "DEAD 게이트 wire" 미완분(frame_status/density)은 가재 교훈상 *1소스보다 먼저.*
2. **(추가 후보) ② 영수증 가시화 B1·B2** — **단, 앞문(로그인/가입) 수리가 선행**인지 확인.
   앞문이 풀렸으면 B1(영수증 카드)부터. 저비용·고효과·스파인 안전.
3. **tmux** — 옵션, 내 작업 편의용.

> **이 문서를 읽는 다음 세션에게:** ①은 중복이면 무시. ②는 앞문 상태 확인 후 진행.
> 둘 다 "새 엔진"이 아니라 *정리/전시*에 가깝다 — 비용 낮음, 되돌리기 쉬움.
