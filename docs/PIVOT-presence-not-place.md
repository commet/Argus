# 피벗 제안 — 장소가 아니라 존재 (Presence, not Place)

> **지위:** 2026-06-10 세션의 결론 스냅샷. 다음 세션이 이어받기 위한 문서.
> 선행: `RESEARCH-market-needs-2026-06.md`(시장 리서치) · `FRAMEWORK-decision-navigation.md`(프레임) · `EXECUTION-PLAN-flinch-spine.md`(기존 실행 계획).
> **이 문서는 기존 계획을 대체하지 않는다 — 게이트(§5)를 통과하면 대체 후보가 된다.**

## 1. 이 결론에 도달한 경로 (요약)

1. **냉철 평가:** Argus의 루프(Flinch→Seal→Return→Ledger)와 zero-verdict 원리는 독창적. 그러나 구조적 약점 3개 — ① 고통이 결정 시점에 안 느껴짐(비타민이 진통제 자처), ② day-1 가치는 ChatGPT 프롬프트로 복제 가능하고 해자(자차표)는 수개월 뒤에야 존재, ③ 깔때기가 좁음(브리프를 글로 쓰는 사람 × 탐침받을 의향 × 정산하러 돌아옴).
2. **시장 리서치 4갈래** (`RESEARCH-market-needs-2026-06.md`): 2024–26 승자 14개 중 12개가 "해결된-척-망가진 것" 또는 "마찰 10배 절감". 무덤의 사인 1위 = **입력 마찰**. 이긴 래퍼 공식 = 게으른 입력 → 모델 → 완성 산출물. LLM이 다시 여는 무덤 = 입력 마찰로 죽은 카테고리들(개인 CRM, 노트 회수, 결정 저널).
3. **1차 조언(workslop 검수 피벗)은 기각됨** — 정당한 기각. 그것은 레버(진입 표면)지 제품이 아니고, 루프가 없어 복리되지 않으며, 창업자의 지적 코어(zero-verdict, 자차표)가 안 산다.
4. **재진단:** 바꿔야 할 것은 영혼이 아니라 **형태**. 현재 형태의 전제 — "사람이 결정의 순간에 웹사이트라는 장소로 가서 브리프를 써서 넣는다" — 가 리서치가 찾은 모든 사망 원인과 충돌한다. 결정 저널들이 죽은 이유와 동일. **결정은 이미 AI와의 대화 속에서 일어나고 있다** — 창업자 본인의 결정도 웹앱이 아니라 Claude Code 세션 안에서 일어났고, 그 잔해가 `.argus/sessions/`와 `~/.claude/projects/`에 쌓여 있다.

## 2. 제안 — Argus의 새 형태

**결정을 입력받는 앱이 아니라, 사용자가 이미 AI와 나눈 대화에서 결정을 스스로 발견하고, 봉인을 제안하고, 날짜에 돌아오는 원장.**

경험:
- **입력 0.** Argus가 (허락 하에, 로컬에서) AI 대화 기록을 읽고 결정의 순간을 *알아본다* — "~하기로 했다", 옵션 비교 후 선택, 방향 전환의 언어. 짖지 않고 알아보는 개.
- **하루의 끝에 한 줄:** "오늘 결정 2개 했더라 — ①… ②… 봉인할래?" 탭 한 번 = 봉인. 반증 신호와 check_by는 대화 맥락에서 자동 초안, 사용자는 수정만.
- **제품이 먼저 돌아온다:** check_by에 "그래서, 어떻게 됐어요?" [발생/회피/부분/아직].
- **자차표가 진짜로 쌓인다** — 원래 설계의 치명 순환(원장이 가치인데 원장은 수동 봉인의 누적이고 아무도 수동 봉인 안 함)이 수확 자동화로 풀림.

영혼 보존 확인:
- zero-verdict 그대로 — "너 X 결정했더라"는 판정이 아니라 관측. 봉인 = 자기 언어화. 귀환 = 질문.
- 측정-거울(시험 항해)은 죽지 않음 — 큰 결정 감지 시 "출항 전에 N척 띄워볼래?" **opt-in 심화**로 위치 이동. 진입 관문이 아님.
- 구조적 약점 3개 동시 해소: 입력 마찰 0 / 깔때기 = AI랑 대화하는 모든 사람 / "내 대화 전체에서 결정을 발견하고 날짜에 돌아오는 존재"는 프롬프트로 복제 불가.
- 유통: 첫 서식지 = Claude Code 플러그인 생태계 (창업자가 이미 깊이 들어가 있는, AI-결정 밀도 최고의 커뮤니티).
- 리서치 정합: AI 대화 무덤(횡단 = 내구·무주공산), 약속 추적(교차 객체 주인 없음), 벤더 비흡수(모델 회사는 사용자 캘리브레이션이 아니라 사용량을 최적화).

## 3. 창업자의 명시되지 않았던 니즈 (이 세션에서 합의된 추론)

1. 창업자가 Argus의 첫 사용자이고, 피치의 두 외로움은 자전적이다. 두려움 = "이게 나만의 결핍이면 어떡하지."
2. 유틸리티가 아니라 **아이디어를 세상에 내는 것**이 정체성 차원의 요구 — zero-verdict 코어가 살아야 한다.
3. 긴장: 계획/프레임워크 만들기가 가장 편안한 모드이고 시장 접촉은 계속 게이트 뒤에 있다. 반증 게이트가 시장을 만나기 위한 장치인지 만나지 않아도 되게 해주는 장치인지의 경계는 얇다.
4. 따라서 진짜 니즈: **지적 코어를 죽이지 않으면서 실사용자 접촉이 구조적으로 빨라지는 형태.**

## 4. 이 방향의 약점 (미리 박아둠)

1. **감시감** — 대화를 읽는 존재는 섬뜩할 수 있음. 완화: 로컬 처리, 결정 후보의 사용자 승인 구조, 개인 데이터는 절대 레포/서버로 안 나감 (레포가 public임에 유의).
2. **감지 정밀도** — 결정 아닌 걸 결정이라 하면 신뢰 즉사 (거울의 "뻔한 갈림" 문제와 동형).
3. **플랫폼 의존** — Claude Code 생태계 첫 서식지의 리스크. (완화: 트랜스크립트 포맷은 추상화, ChatGPT 내보내기 등 횡단이 오히려 내구 슬리버.)
