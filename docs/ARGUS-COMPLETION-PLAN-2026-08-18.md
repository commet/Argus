## 0. 완성이 무엇인지부터 정한다

지금까지 "완성"이 한 번도 정의된 적이 없다. 그래서 기능이 늘 때마다 완성이
멀어졌다. 여기서 정한다:

> **완성 = 결정 하나가 들어가서, 기한이 오면 제품이 먼저 찾아오고, 그 자리에서
> 실제로 무슨 일이 있었는지가 기록되고, 다음 판단에 규칙 한 줄이 남는 것.
> 그리고 그 한 바퀴가 실제로 도는 것을 관측한 것.**

기능 목록이 아니라 **한 바퀴**다. 이유는 `ARGUS-PRODUCT-PLAN-2026-08-05.md` §2가
이미 적었다 — 계획 생성은 상품화됐고 방어 가능한 것은 정산 하나뿐이다.
같은 문서 §6이 그것을 **"H-B · 증거 0건 — 사업의 전부"**라 부른다.

## 2. 왜 한 바퀴가 안 돌았나 — 오늘 찾은 것

15바퀴를 돌렸는데(`docs/receipts/2026-08-11-first-user-journey/`) `plan_check`가
0회다. 지금까지 이것을 **모델의 동사 선택 문제**로 적어 왔다(11차 종결:
*"문맥 손잡이는 내용 보존까지 바꾸지만 동사 선택은 못 바꾼다"*).

그 진단이 틀렸다. 이유는 훨씬 단순하고, 제품이 아니라 **계측기**에 있다.

> **여정 하네스에는 시계가 없다.**

- 하네스의 "재시작"은 **프로세스 재시작**이지 날짜 이동이 아니다
  (`evals/first-user-journey.mjs`, 7단계: 서버를 닫고 다시 연다).
- 계획 단계는 `+7d`·`+2w` 지평으로 채택된다 → 확인일은 **일주일 뒤**.
- 그래서 8단계의 `check_in`은 **옳게** 침묵한다. 마감 전이니까.
- 확인일이 온 적이 없으니 `plan_due` 표면이 뜬 적이 없고, 뜬 적이 없으니
  모델이 `plan_check`를 부를 계기가 **구조적으로 존재한 적이 없다**.

리시트가 이 원인을 이미 적어 놓고도 결론을 못 냈다 — *"check_in은 침묵 계약대로
조용했고(마감 전이라 옳음)"*. 계측기가 자기 맹점의 원인을 **정상 동작으로**
기록한 것이다.

**그리고 시계는 이미 있다.** `today_override`가 `resolveToday()`의 첫 번째
인자이고(`lib/resolve-today.ts:15`), 서버가 공개 스키마에서 감춘 채
받아들이며(`server.ts:141-143`, `public-tools.ts:549`), 결정론 배터리는
이미 이것으로 시간여행을 한다(`evals/battery.mjs:63`,
`evals/ambient-picker.mjs:118`). **라이브 여정 하네스만 한 번도 쓰지 않았다.**

> 15바퀴 동안 사업의 전부라 불린 가설이 계측기의 사정거리 밖에 있었다.
> 그리고 사정거리를 늘리는 부품은 처음부터 서랍에 있었다.

### 1b걸음 — 모델 없는 대조군 ✅ 완료 (PR #399)

라이브 실행에는 모델이 필요하고 모델은 비싸고 흔들린다. 그 전에 **모델을 빼고
시계만 돌려** 제품 쪽 호가 실제로 도는지 확정했다. 대조군 없는 라이브 측정은
원인을 못 가른다 — 이것이 초록이면 라이브의 빨강은 오직 모델의 라우팅이다.

`argus-mcp/evals/battery.mjs` 에 시나리오 셋, **전부 첫 실행 초록**:

- **S47** 확인일 전 침묵 → 확인일에 제품이 먼저 말을 건다 → `plan_check` →
  **적은 단계는 다시 안 묻는다**
- **S48** 날짜 단계 6개라도 예약은 정확히 3개, 표면이 그 사실을 스스로 말한다
- **S49** 정산으로 닫힌 결정은 단계를 더 묻지 않는다 (거울 조항)

```bash
cd argus-mcp && npm run build && node evals/battery.mjs      # 116 calls · 0 RED
```

> **판정: 귀환 기계는 돈다.** 한 번도 관측되지 않은 것은 "모델이 그것을 쓰기로
> 고르는 것"이다.

### 2걸음 — 첫 라이브 관측 ⏳ (API 키 있는 환경에서 명령 한 줄)

```bash
export ANTHROPIC_API_KEY=...
cd argus-mcp && npm run build
for P in 3 8; do
  node evals/first-user-journey.mjs --local --script plan --persona $P \
    --out /tmp/journey-plan-p$P
done
# 창업자 배역 (11차에서 가장 아팠던 프로필)
node evals/first-user-journey.mjs --local --script plan --persona 8 \
  --traits cog_directness=Blunt,cog_verbosity=Terse,cog_formality=Casual,cog_patience=Low,cog_conflict_approach=Confronting,decision_style=Directive \
  --out /tmp/journey-plan-founder
```

`--traits` 는 **`축id=값` 쌍**이다 (`persona-sampling.mjs` 의 `AXES`). 축 이름이나
값 하나만 틀려도 하네스가 유효 목록을 찍고 `exit 2` 한다 — 이 문서의 첫 판이
바로 그 형태로 틀려 있었고, 명령이 안 도는 계획은 계획이 아니다.

**먼저 확인할 것** — `summary.json` 의 `time_travel.session2_today` 가 `null` 이
아니어야 한다. `null` 이면 계획이 날짜 없이 채택된 것이고, 그 실행은 `plan_check`
관문을 **측정하지 못한 것**이지 실패한 것이 아니다.

**결말은 셋이고 각각 다음 작업이 다르다**:

| `summary.json` 이 말하는 것 | 읽는 법 | 다음 |
|---|---|---|
| `ledgerEventCounts.plan_check > 0` | **한 바퀴가 처음 돌았다** | 4걸음으로 |
| `plan_check == 0` 인데 세션2 도구 목록에 `argus_check_in` 호출이 있다 | `plan_due` 는 떴는데 모델이 다른 도구로 샜다 — 11차 "동사 선택" 진단이 **이번엔 증거를 갖는다** | 3걸음: 손잡이를 모델이 이미 향하는 도구 안에 둔다 |
| 세션2에 `argus_check_in` 호출 자체가 없다 | 문제는 귀환 기계가 아니라 **진입**이다 | 3걸음 아님 — 호스트가 세션 시작에 무엇을 보는가 |

무엇이 나오든 `docs/receipts/` 에 적는다. 관문 점수만 적고 트랜스크립트를
안 남기면 다음 사람이 같은 오독을 반복한다.

**5번만 먼저 한 이유**: 앞의 넷은 *고장난* 것이고 5번은 *없는* 것이었다. 그리고
없는 그것이 §0 이 정의한 완성의 마지막 문장 — "규칙 한 줄이 남는다" — 그 자체다.
측정이 무엇을 말하든 그 고리가 없으면 완성이 성립하지 않으므로, 측정 대기 대상이
아니었다. (설계·검증은 [리시트 §4·§5](./receipts/2026-08-18-loop-clock/README.md).)

### 4걸음 — 창업자 1회 완주 ⏳ (실제 달력, H-B 첫 증거)

시뮬레이션은 시뮬레이션이다. `today_override` 로 도는 바퀴는 **기계가 기한을
인식하는가**를 재지, **사람이 기한에 돌아오는가**를 재지 않았다. 후자가 H-B 이고
증거는 오늘까지 **0건**이다.

**대본** (창업자 본인, 실제 결정 하나):

1. **오늘** — Claude Code 나 Desktop 에서 평소처럼 결정 하나를 꺼내 말한다.
   도구를 지목하지 않는다. 지목하면 "진입"을 못 재게 된다.
2. 계획을 받으면 **기한을 짧게** 잡는다 (`+2d`). 실제로 이틀 뒤 확인 가능한
   단계여야 한다.
3. **이틀 뒤** — 아무것도 준비하지 않고 터미널을 연다. 평소처럼 일을 시작한다.
4. 그 자리에서 **제품이 먼저 말을 거는지** 본다. 걸면 결과를 말한다.
5. 원장을 눈으로 대조한다. 원장 위치는 **git 저장소 안이면 그 프로젝트의
   `.argus/`, 아니면 `~/.argus/`** 다 (`argus-dir.ts` 의 해석 순서):
   ```bash
   L="$(git rev-parse --show-toplevel 2>/dev/null)/.argus/ledger/ledger.jsonl"
   [ -f "$L" ] || L="$HOME/.argus/ledger/ledger.jsonl"
   grep -c '"event":"plan_check"' "$L"   # 0 이면 그 자리에서 안 적힌 것
   grep -c '"lesson"'            "$L"   # 규칙이 남았나
   ```

**무엇을 적는가** (셋 다 결과다): ① 제품이 먼저 말을 걸었나 ② 그 자리에서
결과를 적었나 ③ 규칙 한 줄이 남았나. 안 걸었으면 **왜 안 걸었는지**가 다음
작업이고, 걸었는데 안 적었으면 그것이 H-B 반증의 첫 증거다.

### 5걸음 — 웹 트랙은 판정만 하고 미룬다 ⏸

`docs/HANDOFF-2026-08-10-DECISION-LOOP-AUDIT.md` 가 웹 트랙의 유일한 완성 기준
(DLP-1~10)을 갖고 있다. 확인한 것: **DLP-2·5는 수리됐다**(커밋 746eb959·361d4db6,
#370 에서 대기 중). **나머지 8건은 08-10 이후 아무 기록이 없다** — 각각 이미
고쳐졌는지 판정하고 기록만 한다.

미루는 근거는 둘이다. 하나는 **창업자 결정 2**(무게중심 = 동반자, 1차 표면은
MCP 도구·플러그인 훅이고 웹은 정산과 거울 — `ARGUS-CANON.md` §9). 다른 하나는
순서다: 웹과 MCP 는 같은 루프의 두 투영이고, 루프가 한 번도 안 돈 상태에서
투영을 고치면 **무엇을 고쳤는지 알 수 없다.** MCP 한 바퀴가 돌면 그 바퀴가
웹의 목록을 다시 써 준다.

단 **#370은 예외로 지금 머지한다** — 이미 초록이고, DLP-2(못 본 문장이 채택으로
새는 것)는 저자성 결함이라 표면 우선순위와 무관하게 `PRODUCT.md` 제약을 어긴다.
그리고 웹의 Lesson 이 그 안에 있다.

- 사용자 10명 (기계 수준 한 바퀴는 돌았지만 사람 한 바퀴가 0건이다 — 4걸음이 먼저)

## 5. 이 계획이 틀렸다고 드러나는 지점

1. ~~시계를 켰는데 `plan_due`가 여전히 안 뜬다~~ → **해소됨.** 1b걸음의 대조군이
   `plan_due` → `plan_check` → "적은 단계는 다시 안 묻는다"까지 전부 초록으로
   확인했다. replay·스케줄링은 의심 대상이 아니다.
2. 2걸음에서 모델이 `check_in` 자체를 안 부른다 → 문제는 귀환 기계가 아니라
   **진입**이고, 다음 작업은 제품 로직이 아니라 호스트가 세션 시작에 무엇을
   보는가다.
3. `plan_check`까지 돌았는데 창업자 실주행(4걸음)에서 아무것도 안 돌아온다 →
   같은 결론(진입). 도구를 꺼낼 이유가 없는 것.
4. 4걸음에서 창업자 본인이 기한에 안 돌아온다 → H-B가 반증된 것이고,
   PRODUCT-PLAN §6이 예고한 축소 지도("첫 세션 가치만 있음")로 간다.
   그건 실패가 아니라 이 제품이 6주 전에 미리 적어 둔 정직한 출구다.
5. 규칙 창이 실제로 열렸는데 아무도 안 쓴다 → 정상일 수 있다(대부분의 귀환에는
   규칙이 없다). **여러 번 연속 빈 제출이면** 묻는 자리가 틀린 것이고,
   `held` 제외 규칙을 더 좁힌다(예: 사용자가 먼저 언급했을 때만).
6. 웹 트랙 8건이 사실은 이미 고쳐져 있다 → 5걸음이 판정만으로 닫힌다.

## 6. 순서

```
0걸음 재고 정리 ─→ [1 ✅ 시계] ─→ 2걸음 첫 라이브 관측 ─→ 3걸음 그 결함만 수리
        │           [1b ✅ 대조군]          │
        │                                   └─→ (3-5 ✅ Lesson 은 선행 완료)
        └────────────────────────────────→ 4걸음 창업자 완주 ─→ 5걸음 웹 판정
```

**4걸음은 2걸음을 기다리지 않는다.** 재는 것이 다르다 — 2걸음은 *기계가 기한을
인식하는가*, 4걸음은 *사람이 기한에 돌아오는가*. 후자가 H-B 이고 그것만이
"사업의 전부"다. 시뮬레이션이 아무리 초록이어도 4걸음의 증거 1건을 대신하지
못한다.

## 7. 이 문서를 갱신하는 때

걸음이 하나 끝날 때마다 **상태 표와 §1 고리 표**를 같이 고친다. 계획이 현실과
어긋난 채로 남아 있으면 다음 세션이 이미 지어진 것을 다시 짓는다 — 이 세션이
`watch` 로 하루를 태운 그 방식 그대로.
