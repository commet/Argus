## TL;DR (자고 일어나서 이거 한 박스만 봐도 됨)

- **나쁜 소식 아님:** 코드 품질은 좋다. 비유도 옳다. 랜딩은 90% 됐다. 엔진도 GREEN이다.
- **진짜 문제 하나:** *통합이 안 됐다.* "다 구현되면 배포"의 "다 구현된 하나"가 존재하지 않는다.
  작업이 3브랜치·2worktree에 흩어졌고 서로 파일을 순환 참조한다. → 형상관리 문제, 기획 문제 아님.
- **루프를 끊는 법:** "전부 완벽"을 기다리지 마라. cut line을 둘로 쪼개라 — **① 정직하게 배포
  가능**(오늘 밤 도달 가능, §3), **② moat 작동**(배포 후 며칠). ①을 먼저 치고 배포해라.
- **오늘 밤 단 하나의 수(가장 고레버리지):** 추상 토론 말고, **파운더 본인이 dogfood로 결정 1건을
  처음부터 끝까지 — 앞문 가입 → 봉인 → (확인일) → 정산 — 실제로 통과시켜봐라.** 그 1건이 막히는
  지점이 진짜 배포 블로커다. 0 sealed → 1 sealed는 완벽한 기획이 아니라 *도달 가능한 한 바퀴*에서
  나온다. (§6 맨 앞 참조.)
- **머지할 때 딱 하나 조심:** `claude-sonnet-4-20250514`(죽은 모델 ID)를 main에 되살리지 마라.

## 0. 한 줄 결론 (루프를 끊는 문장)

**지금 "다 구현되면 배포"라는 그림은 존재하지 않는다 — 왜냐하면 "다 구현된 하나의 브랜치"가
없기 때문이다.** 작업은 3개 브랜치·2개 worktree에 흩어져 있고, 각각 단독으로는 빌드/배포가
안 되며, 서로 파일이 순환 참조한다. 그래서 아침에 "고칠 게 많다"고 느끼는 건 코드 품질 문제가
아니라 **통합(integration)이 안 된 상태를 완성으로 착각**하는 데서 온다.

**좋은 소식: `main`은 깨끗하고 거의 배포 가능한 기준선이다.** 위험은 전부 *아직 머지되지 않은
흩어진 작업*에 있다. 그러니 루프를 끊는 길은 "전부 완벽하게 만들기"가 아니라 **"main을 기준으로,
무엇을 어떤 순서로 안전하게 합치면 정직하게 배포 가능한 한 덩어리가 되는가"를 정하는 것**이다.
그 정의를 §3에 박아둔다.

## 1. 아침에 가장 먼저 아플 5가지 (the 9am headlines)

흥분이 식은 뒤 제일 먼저 보일, 그리고 제일 비싼 것들. 나머지는 다 이것들의 그림자다.

### (A) 작업이 흩어져 있고, 통합된 적이 없다 — 그리고 순환 의존성이 있다
실측한 현재 지형:

| worktree | 브랜치 | 무엇이 있나 | 단독 배포? |
|---|---|---|---|
| `Argus` (메인 체크아웃) | `docs/gjc-borrow-ideas-2026-06-23` | **랜딩 프레젠테이션**(VoyagePhases·PhaseGlyphs·LegBreadcrumb·VoyagePhaseRail·Act2/3) — 전부 **커밋 안 된 untracked/modified** | ✗ (미커밋) |
| `argus-bind` | `feat/bind-phase-1` | **BIND 로직**(BindCard·buildEarlyContract·augmentContract·`user_lean` source·테스트) — 커밋·푸시됨, 단 **page.tsx 배선은 아직 안 함** | ✗ (미배선) |
| `argus-10dim` | `feat/ten-dimensions` | 10-dimensions 작업 + **모델 ID 수정**(claude-sonnet-4-6) | ✗ (별개 작업) |
| — | `main` | 안전한 기준선. 깨끗함. | ✓ (현 라이브) |

**핵심 모순(순환 의존성):** `feat/bind-phase-1`의 `ProgressiveFlow.tsx:78`이
`./VoyagePhaseRail`을 import하는데, 그 **파일은 그 브랜치에 없다** — 그 파일은 *다른* worktree
(메인 체크아웃)에 **커밋 안 된 채** 떠 있다. 즉 BIND 브랜치는 지금 `tsc`가 깨진다. 두 트랙
(로직 / 프레젠테이션)이 서로의 파일을 가져다 쓰는데 한쪽은 커밋 안 됨, 다른 쪽은 파일 없음.
**이게 정확히 "새벽 4시엔 다 된 것 같고 아침 9시에 엉킨 실타래로 보이는" 그 현상이다.**

> **교훈:** 비유나 기능의 문제가 아니라 *형상관리(SCM) 위생*의 문제. §5에 교통정리 절차를 박아둠.

### (B) 랜딩이 제품을 추월했다 — "묶기 먼저"를 약속하지만 제품은 아직 안 그렇다
- **랜딩(프레젠테이션):** 90% 완성. 세 다리(묶기/듣기/닿기)가 명시적으로 *보이고*, 카피도
  스파인 준수(중립 crux 질문, "AI can't decide for you. You confirm." `VoyagePhases.tsx:60-61`).
  비주얼·애니메이션·a11y 다 실재. **거의 다 됐다.**
- **제품(실제 흐름):** 아직 **bind-first가 아니다.** `workspace/page.tsx:291-361`은 제출 →
  곧장 `runInitialAnalysis` → 분석을 *먼저* 보여줌. 사용자의 lean을 *먼저* 잡는 단계가 없다.
  사용자 판단 캡처(`Falsification.real_bet`)는 여전히 **항해 끝**에서 일어난다 — 그건 신화로
  치면 "노래를 다 듣고 나서 밧줄을 묶는" 것, 즉 **Kafka의 자기기만 극장**이다.
- BindCard는 만들어졌지만(`feat/bind-phase-1`) **page.tsx에 배선이 안 됐다.** 즉 랜딩은
  "묶고 듣는다"고 가르치는데 사용자가 실제로 워크스페이스에 들어가면 옛 흐름을 만난다.

> **위험:** 랜딩과 제품이 어긋난 채로 배포하면, 가장 신뢰가 중요한 첫 사용자에게 **"광고와 다른
> 제품"**을 보여준다. 둘 중 하나를 늦춰서라도 *일치*시켜야 한다 (§3의 cut line).

### (C) 익명 사용자 모순 — bind가 채우려는 moat가 바로 그 코호트에게 안 쌓인다
이게 가장 깊고 가장 비싸다. 06-22 UIUX 감사의 헤드라인과 **정확히 동일**하다.

- bind 재설계의 목적: project-OPEN에 `decision_contract`(밧줄)를 일찍 써서 "sealed 0건" 공백을
  메운다.
- 그런데 **익명 사용자의 서버 쓰기는 막혀 있다** (`db.ts:216-217` `if (!userId) return;`).
  익명의 bind/seal은 **localStorage에만** 남고 Supabase엔 0. funnel이 데려오는 사람의 상당수가
  바로 이 익명 콜드스타트 코호트일 것이다. *(주의: 익명 비율은 직접 검증 안 됨 — 라이브 수치는
  13 users / 47 projects만 확인. "대다수"는 커뮤니티 런칭 시 공개 링크로 들어오는 첫 방문자가
  로그인 전 상태라는 일반 패턴에 근거한 추론. P0-4 실주행으로 확정하라.)*
- 게다가 **정산(return) 표면이 익명에게 auth-wall** (`/project`가 `PUBLIC_PATHS`에 없음,
  `AuthGuard`가 가로챔; due 배지도 `Header.tsx:39` `if (user)`로 익명엔 죽음 — UIUX §A 실측).
- 결과: 익명 사용자는 밧줄을 묶어도(이벤트는 `user_events`에 남아 계측은 됨) **그 계약이 서버에
  안 닿고, 확인일에 돌아올 표면도 막혀 있다.** seal→정산 루프가 *바로 그 코호트에게 닫히지
  않는다.* bind를 아무리 예쁘게 앞당겨도 **익명에겐 sealed contract가 여전히 0**일 수 있다 —
  더 일찍 0일 뿐.

> **이건 비유의 실패가 아니라 비유가 정확히 짚어주는 실패다.** Blanchot의 "비겁" — 노래엔
> 노출되지만 *현실(정산)엔 노출되지 않는* 항해. 익명에게 정산이 안 닫히면 그 사용자의 항해는
> 구조적으로 비겁(닿지 못함)이다. **앞문/익명-정산이 bind보다 먼저다.**

### (D) feature 브랜치들에 죽은 모델 ID — 라이브 장애 아님, **머지 회귀 위험**
- `main`은 정상: `route.ts:153-154` = `claude-sonnet-4-6`. **현 라이브는 안 깨져 있다.**
- 그러나 `docs/gjc-...`(현재 브랜치)와 그 위에 쌓인 `feat/bind-phase-1`은 main의 모델-ID 수정
  *이전에* 갈라져서 **stale `claude-sonnet-4-20250514`**를 들고 있다 (현재 브랜치 1 behind main).
- **위험 시나리오:** 이 feature 브랜치들을 main에 머지하면서 route.ts를 덮어쓰면 **고쳐둔 모델
  ID가 되살아나 죽는다** → 머지 직후 라이브 전체 LLM 호출 404. "기능 추가했더니 앱이 죽었다"의
  전형.

> **대응:** 머지 전 무조건 main에 rebase하거나, route.ts/direct route.ts의 모델 ID를 머지
> 후 grep으로 재확인. §5/§7 체크리스트에 박음.

### (E) 앞문(가입)의 코드 밖 단계 — 보이지 않는 배포 블로커
- 코드상 이메일 가입 흐름은 존재(`login/page.tsx`, `/auth/callback`). 명백한 500 경로는 코드만
  봐선 안 보임.
- 그러나 메모리(backend-audit-2026-06-19)에 따르면 **Resend 도메인(argus.voyage)은 검증됐지만
  Supabase SMTP 연결은 "파운더의 수동 단계"로 미완**일 수 있음. 이게 안 됐으면 확인메일이
  안 가고 → 가입 자체가 막힌다 → 워크스페이스/익명은 되지만 *계정 생성 = moat 지속*이 0.

> **검증 액션(파운더):** 실제로 새 이메일로 가입 → 확인메일 수신 → 로그인까지 *한 번* 직접
> 해보고 행이 DB에 늘었는지 확인. 코드로는 못 닫는 사실이다.

## 3. "배포 가능"이 실제로 무슨 뜻인가 — cut line 두 개

루프가 끊기지 않는 진짜 이유: **"완성"의 정의가 무한대로 미끄러지기 때문**이다. 비유가 아름다울수록
"이것도 넣어야 완성"이 끝없이 붙는다. 그래서 *두 개의 명시적 cut line*을 박는다. 위는 "정직하게
배포 가능", 아래는 "moat가 실제로 작동". **이 둘을 섞지 마라.** 위가 먼저다.

### CUT LINE 1 — "정직하게 배포 가능" (Honest-Shippable) = 최소 진실
배포해도 *거짓말이 아닌* 상태. moat가 완벽할 필요 없음. 단지:
1. **하나의 브랜치**가 main에서 빌드되고 (P0-1,2,3 해결).
2. **앞문이 실제로 열림** (P0-4: 가입 1회 성공).
3. **랜딩이 약속한 것을 제품이 하거나, 약속을 톤다운** (P0-5).
4. 라이브 LLM이 안 죽음 (P0-3).

→ 이 4개만 되면 **배포해도 된다.** moat가 아직 안 닫혀도, 그건 "다음 사용자부터 점점 닫히는
중"이지 거짓말이 아니다. **단, 익명 seal 휘발성은 한 줄로 정직하게 고지**(P2-6)해야 거짓말을
면한다. (이게 Honest-Shippable의 "honest" 조건.)

### CUT LINE 2 — "moat가 작동" (Loop-Closing) = 제품이 챗봇과 달라지는 지점
이건 배포 *후에* 점진적으로 도달해도 되는 선. 우선순위는 UIUX 감사의 시퀀스를 따른다:
1. **익명 정산 도달 가능화** (P1-2,3) — *가장 고레버리지, 이게 없으면 나머지가 무의미.*
2. **bind 배선 + seal AUGMENT** (P1-4,5,6).
3. **익명 서버 영속** (P1-1) — 또는 최소한 "로그인하면 네 밧줄이 따라온다"는 eager-migration이
   이미 있는지 확인(메모리상 `0947558` progressive eager-migrate 존재 — 이게 bind 계약도 옮기는지
   재검토).
4. **moat를 사용자가 *느끼게*** (UIUX §D: patterns 카드를 `decision_contract`에서 파생).

> **파운더에게 주는 한 문장:** *오늘 밤 목표는 CUT LINE 2가 아니라 CUT LINE 1이다.* 묶기-듣기-닿기가
> 전부 완벽히 작동하는 걸 기다리면 영원히 배포 못 한다. **"정직하게 배포 가능"을 먼저 치고, moat는
> 라이브에서 실사용자와 함께 닫아라.** 첫 sealed contract 1건은 완벽한 기획이 아니라 *도달 가능한
> 앞문 + 도달 가능한 정산*에서 나온다.

## 4. 비유 자체에 대한 깊은 비판 (다각도 — 흥분을 식히고 본 것)

비유는 강력하고 대체로 옳다. 하지만 *제품 설계로 내려올 때* 생기는 균열이 있다. 새벽엔 안 보이는
것들.

### 4.1 콜드스타트엔 Circe가 없다 (가장 중요한 균열)
신화에서 밧줄을 *미리, 차분할 때* 묶는 건 **Circe라는 사전 신뢰(이미 이 해협을 통과한 안내자)**가
있기 때문이다. 그런데 **처음 온 Argus 사용자에겐 Circe가 없다.** 그들은 *노래를 들으러* 왔다 —
그게 그들을 데려온 동기다. 그 사람에게 "노래 듣기 전에 네 입장부터 한 줄 묶어라"는 건:
- 사용자의 동기(빨리 답/통찰을 듣고 싶다)와 **역행**한다.
- 아직 아무 가치도 못 받은 상태에서 **노동(타이핑)을 먼저** 요구한다 (friction-first).
- 그래서 **dominant skip이 대부분 눌릴** 공산이 크다. 그러면 bind-at-open도 contract 0 →
  "더 일찍 0"일 뿐, 문제 미해결.

> 문서(`MYTH...`)는 "초기엔 Argus-제품이 Circe다"라고 *주장*하지만, **UX가 그 신뢰를 밧줄을
> 요구하기 *전에* 세우지 않는다.** 신화의 전제(사전 신뢰)가 콜드스타트에 빠져 있다.
>
> *반론(공정하게):* 랜딩 자체가 Circe 역할을 *어느 정도* 한다 — 항해를 미리 보여주고 "AI는
> 못 정한다, 네가 확인한다"를 약속해 신뢰를 깐다. 그래서 랜딩을 충분히 본 사용자에겐 bind가 덜
> 갑작스러울 수 있다. **하지만** 그건 *랜딩을 끝까지 읽은* 사용자에 한하고, 딥링크(`?q=`)·바로
> 워크스페이스로 오는 사람에겐 Circe가 없다. plan은 "?q= 딥링크도 bind ON" 결정을 했는데(§5),
> 이게 바로 *Circe 없는 사용자에게 밧줄부터 요구*하는 경우다. → 이 코호트의 skip률을 P1-8로
> 반드시 측정. 추측 금지.
>
> **설계 함의:** bind를 "가치 이전(pre-value) 관문"으로 두면 활성화에 세금. 대안 — (a) bind를
> 분석 스트림과 *겹쳐서*(이미 plan에 있음) 사용자가 "읽혔다"는 가치를 먼저 느끼게 하되 밧줄은
> 그 위에 얹기, (b) 또는 **묶기를 첫 비트가 아니라 *분석 직후 인식 비트*로** 두기 — 이건 다음 균열로
> 이어진다.

### 4.2 Bind vs Mirror — Phase 1의 첫 비트가 두 문서에서 다르게 정의됨
두 감사가 "항해의 앞"에 서로 *다른* 것을 두라고 한다:
- `PLAN-3phase`(묶기): **Bind** = 사용자가 *자기* lean을 *AI 전에* 작성 (active, user-authored).
- `UIUX-AUDIT §B`: **Mirror** = AI가 *사용자가 말 안 한 숨은 가정 하나*를 제시 (ai_surfaced, 인식).

이 둘은 **다른 비트다.** Mirror는 분석 출력이 있어야 가능(AI가 가정을 추출해야). Bind는 분석
*전*. 그래서:
- 사용자가 워크스페이스에서 처음 만나는 것이 **빈 "네 입장 적어" 카드(Bind)**인가,
  **"이게 네가 말 안 한 전제야(Mirror)"**인가? 둘은 심리적으로 정반대 — 하나는 요구, 하나는 선물.
- Mirror가 활성화(4.1의 friction)를 훨씬 덜 낸다. *주는 것*이니까. 하지만 moat(사용자-저작
  밧줄)는 Bind라야 채워진다.

> **이건 진짜 미해결 설계 충돌이다.** 두 세션이 각자 "앞 비트"를 만들면 충돌하거나 둘 다 앞에
> 쌓여 무거워진다. **재검토에서 반드시 확인:** 실제 흐름의 첫 인터랙션이 Bind인지 Mirror인지
> 하나로 정해졌나? (권고: Mirror를 먼저 *주고*(선물=신뢰 구축=4.1의 Circe 대체), 그 인식 직후에
> Bind를 *얹는다* — 신뢰가 선 뒤 밧줄을 요구. 순서가 곧 활성화율이다.)

### 4.3 "닿기(Land)"가 시간성이 다른 두 가지를 한 단어에 뭉갰다
`Land/닿기`가 지금 두 개를 담는다:
- (a) **Scylla/Charybdis** — *그 순간*의 불가역·손실 있는 선택 (a moment).
- (b) **Settlement** — 확인일에 현실과 대조하는 *긴 시간*의 정산 (a long arc).

이 둘은 시간 척도가 다르다. 한 단어로 묶으면 제품에서 흐려진다: 사용자는 "닿기"가 *지금 결정하는
것*인지 *나중에 채점하는 것*인지 헷갈린다. UIUX 감사도 "Synthesize가 intro에선 이타카, body에선
조율"(§2.3-6) 같은 이름 충돌을 잡아냄 — 같은 종류의 균열.

> **권고:** 닿기 안에서 *순간의 선택*과 *시간의 정산*을 시각적으로/언어적으로 구분하거나, 닿기는
> "정산(긴 호)"에만 쓰고 Scylla(순간)는 듣기→닿기 *사이의 전이*로 따로 명명. 한 화면 한 의미.

### 4.4 Blanchot의 "비겁" 비판이 익명에게 *구조적으로* 적중한다 (4.1·C와 연결)
"결론을 안 바꾸고 노래를 안전하게 듣는다"가 미덕(개=진실을 보는 자)인가 회피인가? 신화의 답:
*노래엔 안 노출돼도 **현실(정산)엔 노출**되니까 비겁이 아니다.* **그런데 익명 사용자는 정산이
안 닫힌다(C, P1-2).** 즉 익명의 항해는 *현실에 노출되는 단계가 막혀 있어* **구조적으로 Blanchot의
비겁**이 된다 — 노래만 듣고 끝. 비유가 자기 제품의 가장 큰 구멍을 정확히 가리키고 있다.

> **이게 §1-C를 "기능 구멍"에서 "정체성 위반"으로 격상시킨다.** 익명 정산을 닫는 일은 편의가
> 아니라 *제품이 비겁(=챗봇)이 아니게 만드는 일*이다. 최우선.

### 4.5 스파인의 잔여 모순 — bind의 skip이 dominant일수록 moat는 0에 수렴
스파인(zero judgment)은 skip을 *무조건* 보장하라고 한다(옳다, tiredest user 보호). 동시에 제품의
존재 이유는 사용자-저작 밧줄(moat)이다. **이 둘은 같은 다이얼의 양 끝이다:** skip을 강하게 할수록
정직하지만 moat는 비고, moat를 강요하면 스파인 위반(forced-typing gate). plan은 "instrument
first_read"로 *측정*하자고만 하고 *해결*하진 않는다.

> 해결은 아마 "강요"가 아니라 **"가치 후 요청"(4.2 권고: Mirror로 신뢰 선물 → 그 위에 bind)**과
> **bind의 보상을 그 자리에서 보여주기**(IDEAS-gjc B3: "봉인 = 미래 영수증 발행 약속"을 즉시
> 시각화)다. skip률을 낮추는 건 압박이 아니라 *그 순간의 납득*이다. 이건 스파인 안전(over-fire
> 아님 — 사용자가 이미 연 결정의 다음 단계 안내).

### 4.6 비유를 *얼마나* 보여줄 것인가 — 간판(signboard)이 되면 스파인 위반
ARGUS-FINAL-DIRECTION은 못박는다: 제로-저지먼트는 **엔진(빌더용 게이트)이지 간판(사용자에게
인식론을 강의하는 랜딩 카피)이 아니다.** "Demonstrate orientation; do not narrate the theory."
그런데 세이렌/밧줄/Circe/Scylla 비유는 *너무 매혹적*이어서 **랜딩에 다 쏟아붓고 싶은 유혹**이 크다.
- 너무 많이 노출 → 사용자에게 "신화학+인식론 강의" = 간판화 = 스파인 위반 + 진입장벽.
- 너무 적게 → "rope vs wax"라는 *유일한 구조적 차별화*(MYTH §2: 경쟁사는 다 wax를 판다)가
  전달 안 됨.
- 현재 랜딩 감사: 세 다리(묶기/듣기/닿기)가 *명시적으로* 보이고 글리프·카피까지 있다. 이건
  비유를 **체험**시키는 쪽(좋음)인가, **설명**하는 쪽(위험)인가? 경계가 모호하다.

> **재검토 점검:** 랜딩이 비유를 *작동시켜 보여주나*(한 결정이 실제로 묶이고-들리고-닿는 걸 보여줌),
> 아니면 *비유를 해설하나*(세이렌이 누구고 밧줄이 무슨 뜻인지 설명)? 전자는 유지, 후자의 문장은
> 잘라야 스파인을 지킨다. **사용자는 항해를 *겪어야* 하지, 오디세이아 강의를 들으면 안 된다.**

### 4.7 메타 — 무한루프의 정체, 그리고 그것을 끊는 것 (이 검토의 핵심)
파운더가 몇 달째 반복한다는 그 루프 — *밤에 비유를 떠올려 흥분 → "다 되면 배포" → 아침에 고칠 것
산더미 → 배포 무기한 연기.* 이걸 거리를 두고 보면:

> **이 루프는 Argus가 고치려는 결정 병리, *바로 그것*이다.** 봉인(아이디어 확정)은 매번 하는데
> 정산(배포=현실 접촉)엔 한 번도 닿지 못하는 항해. Blanchot의 비겁(노래는 듣되 현실엔 노출 안 됨),
> Kafka의 극장(완벽한 의례, 현실 미접촉). **파운더 자신이 Argus의 1번 사용자이고, 지금 그 사용자의
> 항해가 닿지 못하고 있다.** ([[harbor-and-voyage]]: "아직 떠날 의향이 있는가"의 자기진단.)

여기서 두 가지가 따라온다:

1. **비유는 *방향*엔 최고지만 *완료 판정*엔 독이다.** 비유가 풍부할수록 "이것도 넣어야 진짜 완성"이
   무한히 붙는다(Scylla도, Circe도, 4명의 해석자도 다 구현하고 싶어진다). 그래서 "완성"의 정의가
   영원히 미끄러진다. 메모리(plugin-hardening): *추상=방향확정(이미 끝남), 디테일은 짓고 실사용으로만
   잡힌다.* → **완료는 비유로 판정하지 마라. cut line 1(§3)이라는 *기계적 체크리스트*로 판정하라.**
   비유가 아무리 더 아름다워질 수 있어도, cut line 1의 4개가 그린이면 배포한다. 끝.
2. **cut line 1을 치는 것 = 파운더 자신의 결정을 정산하는 것.** 배포라는 현실 접촉에 *닿는* 순간,
   파운더는 자기 제품의 첫 번째 닿기(Land)를 완성한다. 그게 0→1이고, 그게 demystification의 시작
   (MYTH §4-④: 정산 한 건마다 세이렌의 omniscience가 한 점씩 깎인다 — 여기선 "이번에도 안 될 거야"
   라는 자기 세이렌이 깎인다). **배포 자체가 이 제품의 가장 정직한 dogfood다.**

> 그러니 이 문서의 가장 큰 권고는 기술적이지 않다: **오늘 밤은 비유를 한 줄도 더 아름답게 만들지

## 5. 흩어진 작업 교통정리 — 안전한 통합 절차 (지휘자 노트)

> **목표:** main을 깨지 않고, 흩어진 가치를 *하나의 검증된 브랜치*로 모은다. ~3시간 뒤 다른
> 세션이 끝나면 이 절차로 정리한다. **원칙: main이 진실, feature는 main에 rebase 후 머지,
> 미커밋은 먼저 커밋하거나 명시적으로 버린다.**

### 5.1 먼저 사진 찍기 (실행 전 상태 보존)
```
git worktree list                      # 3개 worktree 상태
git -C <each> status                   # 미커밋 변경 전수
git stash list                         # 떠도는 stash
git branch -vv                         # 각 브랜치 upstream/ahead-behind
```
미커밋 작업(특히 메인 체크아웃의 랜딩 프레젠테이션)은 **버리기 전에 반드시 브랜치로 커밋.**
공유 트리에서 브랜치가 턴마다 바뀌므로(메모리), 미커밋 채로 두면 다른 세션이 덮어쓸 수 있다.

### 5.2 순환 의존성 끊기 (P0-2)

- (권장) 프레젠테이션 미커밋 작업을 **`feat/voyage-presentation` 브랜치로 커밋** → `VoyagePhaseRail`이
  *어딘가에 존재*하게 만든 뒤, 통합 시 BIND 브랜치와 함께 머지.

## 7. ~3시간 후 통합 재검토 프로토콜 (이 문서의 두 번째 용도)

다른 세션들이 끝난 뒤 지휘자로서 전수 점검할 절차. 각 단계 결과를 이 문서 옆에 기록한다.

0. **먼저: 다른 세션이 *정말* 끝났는지 확인 (안 끝났으면 통합 실행 금지).** 공유 트리에서 아직
   도는 세션의 worktree를 건드리면 충돌·작업 유실. 판단 근거 — 최근 커밋 타임스탬프
   (`git -C <wt> log -1 --format=%cr`)가 멈췄나, 미커밋이 *변하는 중*인가(잠시 후 재확인). 활발히
   변하면 **읽기-검토만 하고 통합은 다음 차례로 미룬다.** 검토(읽기)는 항상 안전, 통합(쓰기/머지)은
   조용해진 뒤.
1. **지형 재촬영:** `git worktree list`, 각 worktree `git status`, `git branch -vv`,
   `git log --oneline --all -30`. 무엇이 새로 커밋/머지됐나.
2. **§2 체크리스트 전수 채점:** P0~P3 각 항목 `[해결/부분/미해결]` + 근거 file:line 또는 커밋.
   특히 P2(스파인)는 git log에 관련 커밋이 많으니 *실제로* 닫혔는지 코드 확인.
3. **main 대비 diff:** 각 feature 브랜치가 main에 머지됐나, 안 됐으면 §5로 통합.
4. **회귀 가드(§5.4) 실행:** 모델-ID grep, tsc, build, 순환의존.
5. **랜딩↔제품 정합(P0-5) 실측:** 워크스페이스 실제 첫 비트가 랜딩 약속과 같나.
6. **익명 루프 실측(C/P1):** 익명으로 bind→seal→(확인일 시뮬)→정산 표면 도달이 *가능한가* 코드
   추적. `db.ts:216`·`PUBLIC_PATHS`·`Header.tsx:39` 변화 확인.
7. **보완 계획 수립 → 안전 실행:** CUT LINE 1을 막는 것부터. 미커밋은 먼저 커밋. 머지마다 검증.
8. **커밋·푸시.** 통합 브랜치 푸시 + 이 문서에 "재검토 결과" 섹션 추가 커밋.

> **교통정리 철칙(공유 트리 안전):** `git add -A` 금지(다른 세션 미커밋 섞임) — touched files만
> surgical add. 브랜치 전환 전 현 worktree 미커밋 확인. 파괴적 명령(reset --hard, checkout --,
> push --force) 전 한 번 더 보존책 확인.
>
> **롤백 안전망:** 통합은 **새 브랜치 `feat/3phase-integration`에서만** 한다 — main/기존 feature
> 브랜치를 직접 안 건드리면 잘못돼도 그 브랜치만 버리면 된다. 통합 시작 전 `git tag preflight-base-<ts>`로
> 기준점 박아두면 언제든 복귀 가능. main에 직접 커밋·push 금지(검증·정합 끝나기 전까지).
