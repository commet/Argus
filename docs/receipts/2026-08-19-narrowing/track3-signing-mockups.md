# 3트랙 — 서명 순간의 목업 3종 (같은 하루, 세 방식)

> 목적: "AI가 결정 후보를 자동 수집하고, 사람은 서명만 한다"에서 **서명을 언제
> 내미는가**를 이론이 아니라 손맛으로 고르게 한다. 코드 0줄 — 전부 목업.
>
> 가상의 하루는 이 저장소의 실제 하루(2026-08-19)를 각색했다: 창업자가 아침
> 세션에서 지시를 내리고, 낮에 판정 셋을 말하고, 저녁에 에이전트 하나가 그중
> 하나를 거스르려 하고, 어제 심은 결정 하나의 확인일이 오늘이다.
>
> 세 방식 모두 공통 전제: 수집은 자동(마찰 0), 서명은 y/엔터 한 타(마찰 1),
> 후보는 발화 자제 게이트를 통과한 것만 (하루 2~4건 가정 — 2b 백테스트가 검증).

---

## A안 — 세션 끝 요약형

하루 종일 아무것도 묻지 않는다. 세션을 닫을 때(또는 `/argus wrap` 한 번) 몰아서:

```
$ (세션 종료 감지)

── argus ──────────────────────────────────────────────
오늘 확인일이던 것 1건:
  ◆ "봉인 4건을 이번 주 정직하게 정산한다" (어제 결정)
    첫 단계 '오늘 O4 판정문 확인' — 실제로 어떻게 됐나요?
    > 판정문 나왔고 읽었다. ITERATE 로 나옴.        ← 창업자가 씀

오늘 대화에서 결정으로 들린 것 3건 — 남길까요?
  1. "v3는 유지, v4만 삭제한다"          [선택 고정 · 범위: argus-mcp]
  2. "supabase 승인은 다시 묻지 않는다"    [금지 · 범위: 이 저장소 세션]
  3. "웹 화면은 나중에, 터미널이 먼저다"    [순서 · 범위: 기획]
  서명: 1,2,3 / 일부만(예: 1,3) / 없음 [엔터=전부]
  > 1,3                                    ← 2번은 이미 CLAUDE.md에 있어서 뺌
──────────────────────────────────────── 서명 2 · 15초 ──
```

- 마찰: **하루 1회, ~15초.** 흐름 중단 0.
- 약점: 세션을 안 닫는 사람(터미널 상시 오픈)에겐 안 뜬다. 저녁엔 판정의
  맥락이 식어서 "이게 뭐였더라"가 생길 수 있다. 세션이 여럿이면 요약도 여럿.

---

## B안 — 뜨거운 직후형

판정이 들린 바로 그 턴 끝에 한 줄. 답 안 하면 그냥 지나간다(강요 없음):

```
> 웹 화면은 나중에. 터미널 먼저 제대로 만들자.        ← 창업자가 씀

  (에이전트가 하던 답변을 마친 뒤, 마지막에)
  ┌ argus ─────────────────────────────────────────┐
  │ 결정으로 남길까요: "웹 화면은 나중에, 터미널 먼저"  │
  │ [y=서명 / 엔터=무시]                              │
  └────────────────────────────────────────────────┘
> y
  ✓ 서명됨 · 재확인: 30일 뒤 (바꾸려면 y30 처럼)
```

그리고 저녁, 에이전트가 그 결정과 어긋나는 일을 시작하려 할 때 (모순 감지가
가능한 범위에서 — 2a 백테스트가 검증):

```
  ┌ argus ─────────────────────────────────────────┐
  │ ⚠ 지금 작업(웹 화면 수정)이 오늘 서명한 결정과     │
  │   어긋납니다: "웹 화면은 나중에" (오늘 14:02, 너)  │
  │   [계속=결정 무시하고 진행 / 중단 / 결정 폐기]      │
  └────────────────────────────────────────────────┘
```

- 마찰: **건당 1회 × 하루 2~4건, 각 2초.** 맥락이 가장 뜨거울 때라 판단이 쉽다.
- 약점: 흐름을 하루 몇 번 찌른다 — 자제 게이트가 부실하면 스팸으로 전락
  (확인 창의 죽음). 연달아 판정을 쏟아내는 날엔 성가심이 몰린다.

## C안 — 아침 큐형

수집은 조용히 쌓이고, **다음 세션의 첫머리**에 어제치가 온다. 이미 있는
세션 시작 훅(check-contracts)과 같은 자리:

```
$ claude
── argus · 아침 ───────────────────────────────────────
오늘 확인일 1건:
  ◆ "봉인 4건을 이번 주 정직하게 정산한다" — 첫 단계
    '어제 O4 판정문 확인'은 실제로 어떻게 됐나요?

어제 서명 대기 3건:
  1. "v3는 유지, v4만 삭제"    2. "supabase 승인 안 묻기"
  3. "웹 화면은 나중에"
  [엔터=전부 서명 / 번호 골라서 / x=전부 버림]
> 1,3
──────────────────────────────────────── 서명 2 · 20초 ──
아침이다. 뭐 있나 는 이제 안 쳐도 된다 — 이게 그것이다.
```

- 마찰: **하루 1회, 아침, 자연 경계.** 확인일 알림(원래 기능)과 한 화면에 합쳐짐.
- 약점: 후보가 하룻밤 식는다 — "내가 어제 왜 이랬지"가 B안보다 잦을 것.
  그리고 **어제의 결정이 어제 저녁의 에이전트를 못 지킨다** (서명 전이라
  구속력 0인 채로 밤을 남). 아침 큐가 밀리면 스킵 습관이 생긴다.

## 비교표

| | A 세션 끝 | B 뜨거운 직후 | C 아침 큐 |
|---|---|---|---|
| 마찰 횟수 | 1회/일 | 2~4회/일 (건당) | 1회/일 |
| 흐름 중단 | 없음 | 있음 (2초 × N) | 없음 |
| 맥락 온도 | 미지근 | **뜨거움** | 식음 |
| 서명→구속 지연 | 몇 시간 | **0** | 하룻밤 |
| 스팸 위험 | 낮음 | **자제 게이트에 전부 걸림** | 낮음 (단 큐 비대 위험) |
| 기존 자산과의 결 | wrap 명령 신설 필요 | 훅 확장 | **세션 시작 훅 그대로** |

## 관찰 두 가지 (판정 아님)

1. 셋은 배타적이지 않다 — 현실 제품은 대개 **B(서명)+C(확인일·잔여 큐)** 조합으로
   수렴할 수 있다: 뜨거울 때 서명하고, 놓친 것과 확인일은 아침에. A는 "세션 끝"
   이라는 경계가 이 사용자(상시 오픈)에게 실재하지 않을 가능성이 커 보인다.
2. B의 성패는 전적으로 **하루 몇 번 내미느냐**에 달렸다 — 2b(후보 추출 백테스트)의
   하루당 개수가 이 선택의 실데이터다. 4건 이하면 B가 살고, 수십 건이면 B는 죽고
   C만 남는다.

**다음**: 창업자가 셋(또는 조합)을 손맛으로 고른다. 고른 방식이 서명 UX의
1차 가설이 되고, 첫 실사용에서 검증된다.
