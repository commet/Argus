# 제안 가드 — 한 PR 한 존 (설치 대기)

**이 가드는 아직 설치되지 않았다.** 설치하려면 `zone-purity.test.ts`를
`src/lib/__tests__/`로 옮기면 된다. 설치 여부를 에이전트가 정하지 않는 이유는
재정초 브리프 §5가 에이전트 역할을 **측정**으로 한정하기 때문이다 — 이 가드는
앱 존을 바꾸는 변경이고, 창업자의 결정이다.

## 왜 필요한가 (실측 근거)

`history-scan.mjs`로 `origin/main` 최근 60커밋을 조사:

| 항목 | 값 |
|---|---|
| 존 혼합 커밋 | **6건 (10.0%)** |
| 그 중 CI를 통과해 머지된 것 | **6건 (100%)** |
| 저장소에 존 검사가 있는가 | **없음** — 워크플로·가드 테스트 모두 |
| 규약이 어디에 있는가 | PR 템플릿 체크박스 (사람이 켠다) |

확인 사례: `argus-mcp/src/lib/premises-core.ts`(MIT)와
`src/lib/premises-core.ts`(앱)가 한 커밋에서 함께 수정됨 — 오탐 아님.

## 설계 결정 둘

1. **비교 대상은 머지 베이스**(`git merge-base origin/main HEAD`)다. `HEAD~1`이
   아니라 브랜치 전체를 봐야 PR 단위 규약이 실제로 검사된다.
2. **금지가 아니라 명시 요구다.** 두 존에 같은 로직을 이식해야 하는 작업이
   실제로 있다(premises-core가 그 사례다). 커밋 메시지에
   `zone-exception: <사유>`를 적으면 통과한다. 목적은 **조용한 위반을 시끄러운
   선언으로 바꾸는 것**이지 작업을 막는 것이 아니다 — 막으면 사람이 가드를 끈다.

얕은 클론 등으로 머지 베이스를 못 구하면 **침묵한다**(가짜 초록이 아니라
미실행). 검사할 수 없을 때 통과시키는 것과 검사한 척하는 것은 다르다.

## 3경로 검증 (2026-08-16 실행)

| 상황 | 기대 | 결과 |
|---|---|---|
| 현재 브랜치 (docs만) | 통과 | **통과** (1 passed) |
| MIT+앱 동시 수정 브랜치 (인위 조성) | 실패 | **실패** — `한 브랜치가 MIT + app 존을 동시에 건드린다` |
| 같은 브랜치 + `zone-exception:` 선언 | 통과 | **통과** (1 passed) |

검증은 `origin/main` 기준 임시 워크트리에서 수행했고, 확인 후 워크트리와
브랜치를 제거했다 — 저장소 상태 변경 없음.

## 설치 시 예상 영향

이 PR의 브랜치(docs만)는 통과한다. 과거 위반 6건은 이미 머지됐으므로 소급
실패하지 않는다(가드는 브랜치의 머지 베이스 이후만 본다). 즉 설치해도
**기존 초록이 빨강으로 바뀌지 않는다.**
