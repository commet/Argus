# 계측기에 시계가 없었다 — 그리고 귀환의 마지막 고리 (2026-08-18)

관련: [`ARGUS-COMPLETION-PLAN-2026-08-18.md`](../../ARGUS-COMPLETION-PLAN-2026-08-18.md)
1걸음·3걸음. 실행은 전부 로컬 빌드(`--local` 상당), MIT 존.

## 0. 한 문장

> **15바퀴 동안 `plan_check` 가 0회였던 것은 모델이 안 불러서가 아니라,
> 확인일이 온 적이 없어서였다.**

## 1. 무엇을 잘못 읽고 있었나

11차 종결(2026-08-15)의 판정: *"문맥 손잡이는 내용 보존까지 바꾸지만 동사
선택은 못 바꾼다."* 즉 모델의 라우팅 문제라는 진단이었다.

기계로 확인한 사실:

| 사실 | 어디 |
|---|---|
| 하네스의 "재시작"은 프로세스 재시작이다 (날짜 이동 아님) | `evals/first-user-journey.mjs` 7단계 |
| 계획 단계는 `+7d`/`+2w` 로 채택된다 | plan 대본 5.5·5.7단계 |
| 도래 조건은 `s.scheduled && s.due <= today && !s.checked_on` | `tools/check-in.ts:318` |
| 그래서 세션2의 `check_in` 은 **옳게** 침묵한다 | 리시트 본문: *"마감 전이라 옳음"* |

**계측기가 자기 맹점의 원인을 정상 동작으로 기록해 두었다.** 확인일이 온 적이
없으면 `plan_due` 표면이 뜰 수 없고, 뜨지 않으면 모델이 `plan_check` 를 부를
계기가 구조적으로 존재하지 않는다. 모델의 성향을 논할 자리가 애초에 없었다.

**부품은 처음부터 있었다.** `today_override` 는 `resolveToday()` 의 첫
인자이고(`lib/resolve-today.ts:15`), 서버가 공개 스키마에서 감춘 채 받아들이며
(`server.ts:141-143`, `public-tools.ts:549`), 결정론 배터리는 이미 이것으로
시간여행을 한다(`evals/battery.mjs:63`). 라이브 하네스만 안 썼다.

## 2. 모델 없는 대조군 — 제품 쪽 호(弧)를 먼저 확정한다

이 컨테이너에는 `ANTHROPIC_API_KEY` 가 없어 라이브 여정을 못 돌린다. 그래서
**모델을 빼고 시계만 돌렸다.** 대조군 없는 라이브 측정은 원인을 못 가른다 —
이것이 초록이면 라이브의 빨강은 오직 모델의 라우팅이고, 이것이 빨강이면
모델 얘기를 할 자격이 없다.

배터리에 시나리오 셋 추가(S47~S49). **전부 첫 실행에 초록.**

### S47 — 확인일 전에는 조용하고, 오면 먼저 말을 건다

실제로 돌아온 표면 원문:

```
✓ argus_capture: 계획 3단계를 이 결정에 붙였습니다. 돌아보기 3번이 예약되었습니다.
✓ argus_check_in (2026-07-05, 마감 전): 지금 확인할 차례가 된 것은 없습니다.
✓ argus_check_in (2026-07-09, 확인일):  계획 단계 1개가 확인 날짜에 닿았습니다.
   첫 번째는 "현재 cron 잡의 실패율을 2주치 로그로 센다"입니다. 어떻게 됐는지
   말씀해 주시면 그대로 기록합니다 (argus_capture action=plan_check).
✓ argus_capture (plan_check): 단계 1("현재 cron 잡의 실패율을 2주치 로그로 센다")의
   결과를 그대로 기록했습니다. 예약된 다음 확인: "큐 후보 둘을 재시도·가시성
   기준으로 비교한다" (2026-07-23).
✓ argus_check_in (같은 날 재호출): 지금 확인할 차례가 된 것은 없습니다.
```

마지막 줄이 중요하다 — **적은 단계는 다시 안 묻는다.** 기록이 소비된다는 증거다.

### S48 — 12단계가 12번 잔소리가 되지 않는다

날짜 붙은 단계 6개, 전부 지난 뒤 `check_in`: **알림은 정확히 3개**(`PLAN_MAX_SCHEDULED`).
그리고 표면이 그 사실을 스스로 말한다: *"날짜 있는 단계는 6개지만, 알림이
과해지지 않도록 가장 이른 3개만 잡았습니다."*

### S49 — 닫힌 결정은 단계를 더 묻지 않는다

정산으로 닫은 뒤 `check_in`: 침묵. 거울 조항(닫힌 결정을 다시 여는 것은 과발화).

> **판정: 귀환 기계는 돈다.** 한 번도 관측되지 않은 것은 "모델이 그것을
> 쓰기로 고르는 것"이고, 그것을 재려면 라이브 실행에 시계가 필요하다.

## 3. 라이브 하네스에 시계 (제품 코드 0줄)

- 세션2의 모든 도구 호출에 `today_override` 주입 (`argus_dir` 와 같은 자리).
- 날짜는 **지어내지 않는다**: 원장의 `plan_adopt` 에서 가장 이른 `due` 를 읽어
  그날로 간다. 그 단계는 언제나 `scheduled` 다(예약은 이른 순 3개이므로 최이른
  단계는 항상 포함).
- 스프레드 **뒤**에 놓아 모델이 보낸 날짜를 덮는다. 타임머신은 계측기의 것이다.
- `summary.time_travel` 에 어디로 갔는지 남고, 관문 라벨이 시계 상태를 진다:

```
단계 결과가 원장에 남았다 (plan_check · 세션2 오늘=2026-08-25)
단계 결과가 원장에 남았다 (plan_check · ⚠ 시계 미이동 — 확인일이 오지 않아 측정 불가)
```

**시계를 안 옮긴 실행의 ❌ 는 제품 실패가 아니라 측정 불가다.** 둘을 같은
기호로 적으면 15바퀴를 잘못 읽은 실수를 다시 한다.

## 4. 귀환이 남기는 규칙 한 줄 (CONTEXT.md 의 `Lesson`)

제품의 약속은 *결정 → 현실 → 사용자가 승인한 배움 → 더 나은 다음 판단*이다.
MCP 에 마지막 고리가 없었다 — 웹만 갖고 있었고(PR #370 의
`ContractSettlement.lesson`), 재고 있는 여정은 전부 MCP 위에서 돈다.
#370 본문이 그 이유까지 적어 두었다: *"MCP 쪽 규칙 패리티는 존 경계에
걸린다 — reducer 는 MIT 존이다."* 그 미룬 절반이 이 작업이다.

| 설계 질문 | 답과 근거 |
|---|---|
| 새 이벤트인가 | **아니다.** `settled` 는 종결이라 상태기계가 뒤의 append 를 전부 막는다. 규칙은 정산 **직전에** 묻고 같은 `settle` 이벤트에 실린다 |
| 언제 묻나 | **현실이 예측에서 벗어난 정산만** (`missed`·`partial`·`avoided`). `held` 에 물으면 아무것도 안 움직인 자리에 규칙을 제조한다 |
| 누가 쓰나 | **사용자만.** 확인창 직접 입력이라 모델을 안 거친다 → v2 사다리의 `elicited_user` |
| 표면은 뭐라 하나 | 규칙이 남았다는 **사실만**. 문장을 되읊으면 기계가 저자인 척하는 쪽으로 읽힌다 |
| 안 쓰면 | 그게 정상이다. 거절·취소·빈 제출·호스트 예외 넷 전부 정산은 그대로 |

실제 표면 원문(S50):

```
✓ argus_resolve: 실제 결과를 기록했습니다: 예측이 빗나갔다. 영수증에 예측과
  실제가 나란히 남습니다. 평가는 없습니다. 다음에 지킬 규칙도 당신의 말 그대로
  남았습니다.
```

**`held` 정산(S51)에서는 창이 뜨지 않는다** — 시나리오가 그것을 직접 잰다.

## 5. 새 가드는 전부 주입으로 빨간불 확인

| 주입 | 빨간불 문장 |
|---|---|
| `held` 에도 규칙을 묻게 함 | `held settle opened the rule window — nothing moved, so asking manufactures a rule` |
| 표면이 규칙을 되읊게 함 | `surface re-states the rule back at the user` |
| 영수증 재열람에서 규칙 제거 | `the rule is unreachable when the receipt is reopened` |
| v2 거울에서 규칙 제거 | `귀환이 남긴 규칙도 유실 없이 건너고 elicited_user 등급을 받는다` 실패 |

한 가지는 **빨간불이 안 났고 그대로 적는다**: `settle.ts` 의 `try/catch` 에
rethrow 를 심어도 테스트가 초록이었다. 원인 확인 결과 1차 방어선이 거기가
아니라 `lib/elicit.ts:155` 였다 — 호스트가 던지면 `elicitDetailed` 가 이미
`no_answer` 로 바꾼다. 주석을 그 사실에 맞게 고쳤다(방어선을 자기 것이라
주장하는 주석은 다음 사람을 속인다).

## 7. 정직한 공백

- **라이브 여정은 아직 안 돌렸다.** `ANTHROPIC_API_KEY` 가 이 컨테이너에 없다.
  시계는 코드로 들어갔고 제품 쪽은 대조군으로 확정했지만, **모델이 실제로
  `plan_check` 를 부르는지는 여전히 관측되지 않았다.** 그것이 완성 계획 2걸음이고,
  키 있는 환경에서 아래 한 줄이면 된다:

  ```bash
  cd argus-mcp && node evals/first-user-journey.mjs --local --script plan --persona 3
  ```

- **사람의 귀환(H-B)은 증거 0건 그대로다.** `today_override` 로 도는 바퀴는
  *기계가 기한을 인식하는가*를 재지 *사람이 기한에 돌아오는가*를 재지 않는다.
  후자는 실제 달력으로만 재진다(완성 계획 4걸음).
